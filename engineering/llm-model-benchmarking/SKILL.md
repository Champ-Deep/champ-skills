# LLM model benchmarking

Class of work: build task banks with deterministic checkers, calibrate them, wire a model into the harness, run the bank, report tier verdicts.

## When to Use

Fire whenever Deep asks to score, compare, or assess an LLM against his task suite, mentions the "LLM Bake-off" or "benchmark", wants a new task added to a bank, needs a checker calibrated, or asks how a model is wired into the harness. Also fire when a run's verdict, cost, or PASS/FAIL report is being prepared, and when Deep asks which model a lane should run on: "cheaper" is half the question, the other half is this suite's tier verdict for that model.

## The bank models the work of the person it is for

When Deep asks to assess a model "for the suite of tasks", the suite that matters is the bank modelling his own daily work: vendor and meeting email, notes to task ingest, cold personalization under verified-fact rules, source-only research, decision briefs, ABM plans, issue triage, PR review, bug fixes, feature recreation with hidden tests, long-context decision logs, NDA review, appraisals. The intern bank answers a different question about a different person. When it is ambiguous which bank is meant, say which one you are about to run and why in one line, then proceed.

## Eval sequence v2 is the procedure of record

`/Users/deep/Celsus/Efforts/LLM Bake-off/EVAL-SEQUENCE.md` (stages 0 to 9). Run `python3 test_run.py`, `run.py --bank v2_tasks --selftest` and `judge.py --selftest` before any comparison. Candidates k=3, frontier references k=1, parallel processes share `--root`.

Verdict shape: judge on the tier table, never on an overall mean, because one failed tier hides inside a high average. `Efficient pick per tier` means pass on every run first, then price, then speed: a model that fails a tier once in three runs is disqualified from that tier regardless of its mean. Report basic (tiers 1 to 2) and major (tiers 3 to 4) cost separately, since heavy work skews spend toward output tokens while routine work skews input. State repeats beside every score, because a reference run once and a candidate run three times are different evidence. A hosted model at full precision is a stand-in for the local quantised build only; state that gap rather than transferring its score to the 4-bit file.

## Blind lead-gen pack for a human evaluator

When someone other than Deep runs the models (an intern, Alfiya), hand over a task pack plus rubrics, never prior scores. Keep answer keys and earlier results in a separate Deep-only file and release keys only after coded outputs come back, because a scorer who has seen 1.00 for a model reads its output toward 1.00. Reuse a few fixtures from the existing bank so the old checkers still score them. Pack v1 (24 tasks, 5 categories, tiers 1 to 4) lives in `Efforts/LLM Bake-off/Blind Task Pack v1/`. Deterministic tasks need their key computed in code before it is written down (a hand count of the QA task was checked this way). No GPT-6.1 or Kimi K3 rows exist in the v2 results, so any claim about them starts from the pack run. Two packs have gone to the same tester under near-identical names (Blind Task Pack v1, 2 Nov, 24 tasks x 3 models; Signal Desk Eval Pack v1, 11 Nov, 9 tasks x 8 models). Before routing a key, a score or a question about her outputs, match the counts she reports (tasks x models = answers) against each pack's header and say which key goes, because a thread subject naming one pack is not evidence of which pack she ran. Read the thread's current folder too: a draft staged to ask her may already sit in Sent Items with a promise in it.

## Product-specific pack when the product's prompts are not yours to share

When the target is someone else's pipeline (prompts withheld or licensed), split its model steps first: text-in, JSON-out steps can be tested on any provider now; agentic steps that depend on the vendor's harness (sandbox, web search) are a harness rebuild, so park them in a later replay phase with the inputs and owners named. Mirror each text step with your own prompt and made-up fixtures so the pack can go to a human evaluator without the licence question. Generate fixtures and keys from one data file with asserts (planted error absent from the source, supported claim present, date windows computed), because a hand-written key drifts from its fixture. Include an abstain task and a clean-input task per step: a model that always writes or always flags scores well on error-only tasks. Before freezing a key, read each answer against the prompt's own label definitions and accept every label they make defensible (a claim about a look-alike company is both `contradicted` and `not_in_source`), and make the key's hard-fail text match the pack's scoring line word for word, because a blind scorer applies the stricter one. Map every task to exactly one verdict step in the pack, and say how a task run on only some models (a reliability repeat) counts, or the pass rule cannot be applied. A task pack is not the comparison: when the brief also asks for a provider comparison, deliver it separately with each cell cited to the provider's own docs or marked untested. Compute the pack's worst-case cost in the generator from the same prompts and price table (runs x (chars/4 x input price + output cap x output price)), because a hand figure does not reproduce (Signal Desk said 2.40 USD; the code gave 2.19 at the same prices). Before counting any cache saving, compare each provider's documented minimum cacheable prefix with the real static prefix: Anthropic 5.5 models need 512 tokens, OpenAI 1,024, Gemini 4 4,096, and shorter prompts are silently not cached. Worked example: `Efforts/LLM Bake-off/Signal Desk Eval Pack v1/build_pack.py`.

## Lane vs default from kanban telemetry (free, before any paid run)

When Deep asks how the Hermes lanes perform against default, start from history, not a new run: `Efforts/Active/Hermes Bots/Lane Performance 2026-11-21/lane_perf.py` reads `kanban.db` task_runs read-only, attributes each reviewer verdict to the profile that submitted the card, and links each run to its profile `state.db` session by title and start time for the model actually used. Score on first-pass review approval per task type, never on run counts: block loops (one card had 1,628 blocked runs) swamp any per-run rate. Count input plus cache tokens, since Anthropic reports cache reads outside `input_tokens`. State the selection bias every time: default sends under 10 percent of its cards to review and those are its hardest, and lanes never ran the same cards, so a gap is a lead for a paired bank run, not a verdict. Re-run `python3 lane_perf.py && python3 build_report.py` to refresh.

- A task prompt that demands its own final line ("Finish with one line exactly: ANSWER: ...") conflicts with the `<answer>` footer: a model can put the ids inside the tags and the ANSWER line after them, so the scored deliverable has no ANSWER line and a correct answer scores 0. Before reading a single-model 0.00 as a failure, open `_deliverable.md` beside `_answer.md`. Sonnet 5.5's longctx-decisions 0/11 and munge-csv 0.03 (it wrote `+91 9876543210`, a defensible reading of "+91 followed by the last 10 digits") were both checker defects; fixed in `chk_log` and `chk_csv`, then `--report --rescore` on the saved outputs (run lanes-20261121, pre-rescore copies kept beside the report).
- Arms inside one root finish fast when the bank is saturated: 255 Hermes runs across five arms took 38 minutes and cost about 1 point of the Anthropic week for Opus plus Sonnet k=3, about 4 points of ChatGPT for Sol plus Astra k=3, and $0.40 for DeepSeek V4.1 Flash k=3. Use these to price the next lane run instead of guessing.

- Gemini on Deep's Antigravity plan runs through `hermes_lane.sh antigravity-subscription-directsdk gemini-4-<name>-<effort>` (arms `argon-high-hermes`, `hydrogen-high-hermes`, `neon-high-hermes`); read the live list with `agy models`, since the names Deep hears about ("Carbon") may not be on his account yet. Measured per task on v2_tasks: Hydrogen High about 0.24% of the Gemini weekly bucket and 0.8% of the 5-hour bucket, Argon High about 1.3% of its own weekly bucket. Gate the run on the 5-hour bucket, because the worker lane's Flash fallback draws from it too. A Gemini reply cut off at the output limit comes back as ERR on long-context tasks (2 of 5 runs), which leaves the tier incomplete rather than failed: report it as an operational risk, not a score.
- A time written as "11:00 AM" for the notes' "11 am" trips `nums()` with an invented "00". The meeting-followup checker strips `:00` now; any new checker that counts numbers needs the same exemption.

## SQL and database tasks

`suite/db_tasks.py` (run with `--bank db_tasks`) holds six SQLite tasks. Pattern to reuse: build the fixture in code, compute the key in plain Python from the raw rows (never from the reference SQL), have the checker execute the model's SQL on an in-memory database, and for schema or index tasks probe behaviour (try to break constraints, read `EXPLAIN QUERY PLAN`) instead of reading the DDL. Plant traps the checker can see: case and padding on emails, NULL in a NOT IN list, a WHERE that turns a LEFT JOIN into an inner join, join fan-out. Reasoning models can return empty text with HTTP 200 when hidden reasoning eats the output cap, so a human-run pack must record max output, thinking setting, stop reason and the raw body for any empty or endless run.

## Verifying spoken model names and prices

A price said on a call is usually one endpoint, not the model. Read `GET /api/v1/models/{id}/endpoints` (public, no key) beside the catalog row: on 27 Nov the spoken "0.036" and "0.035" were the cheapest fp4 endpoints and the `~vendor/...-latest` router aliases, while the dated IDs listed at 4x that, and the newer DeepSeek Flash snapshot carried `pricing.overrides` that double it in weekday UTC windows (Indian business hours). Price a ceiling at the highest override, pin `provider.only` with fallbacks off so a row is one endpoint, and never run production on a `~` alias, since it moves to new models without notice. Check `input_modalities` per ID too: a text-only baseline cannot be the OCR step, whatever was said. For a batch recommendation read the batch quickstart first: the window is 24h only, and inline base64 images and files are allowlist-only, so private documents would need public URLs. A `flex` endpoint can list the batch price on the sync API; its slug is the endpoint's own `tag` field (`google-ai-studio/flex`). Worked example: `Efforts/LLM Bake-off/Parser and ESS Eval v1/`.

Price image calls with each vendor's own image tokenizer, never one flat per-page figure: OpenAI's tile table bills `gpt-4o-mini` at 2833 base plus 5667 per 512 px tile (an A4 page at 150 dpi is about 36,800 prompt tokens, about $0.0055 a call), roughly 20 times a flat 1,800 estimate, and it is usually the incumbent OCR fallback. Give each flow's `--max-usd` at least that flow's computed ceiling and keep the flows' caps summed under the key limit, or a run that books unknown cost at worst case stops before the matrix ends. Score numeric fields numerically before any string normalisation that strips the dot (`15` must not match `1.5`), and key only values the fixture text states.

Before writing "engineer not verified" or "production repo not reachable", read who owns the app: `Efforts/Active/Railway Exit/plan.md` (owner column), commit authors of the sibling repos (`git log --all --format='%an <%ae>' | sort | uniq -c`), and `Atlas/People/<name>.md` for the address. Name the evidenced candidate and let Deep confirm, rather than asking him to supply the name from scratch.

## Procedure

0. Before budgeting a run, check whether the bank already has rows for both candidates (`grep -l <slug> suite/results/*/report.md`). Then read the incumbent's production telemetry using the attribution queries in the `model-routing` skill's cost comparison reference: it settles price, calls per task and fires per job, but never quality, so it tells you what the bank has to measure rather than standing in for it. A lane-swap question with no bank rows for either model is untested, and that fact is the first thing to report.
1. Read `docs.md` and `run.py` before writing tasks. The Task shape: prompt, fixtures dict, checker returning a list of `(name, bool)`, a good sample, a bad sample, a tier. Follow it exactly; `run.py` is the contract.
2. Ground fixtures in real vault material (actual NDA clauses, the social-voice rules, real decision formats) so the checks test what Deep's work actually demands. Client names stay fictional-but-plausible; check `_config/link-policy.md` before any wikilink.
3. Calibrate every task with `--bank <bank> --selftest` before any model run: good must score 1.00 and bad must score at or below the discrimination threshold (0.50 in current banks). A bad sample above the threshold means the checker is not discriminating: strengthen the bad sample or tighten the checks until it does. A good sample below 1.00 means the checks reject the answer they were written to accept, which makes every model look worse than it is; fix the checker before running anyone. Also confirm the harness can express a genuine failure: a checker with no `good` sample that would score below 1.00 reports everything as a pass and makes a model look flawless on a task it never handled.
4. Wire the driver per `references/model-drivers.md`, then smoke test ONE task through the full harness before the full run. A lane that answers a prompt has not proven it can edit files and run tests, and a lane that answered has not proven it ran the model you named: read `_usage.json` on the smoke run and compare the model id that came back to the row's key. A driver that drops the auth header still gets HTTP 200, answered by the proxy's own fallback model, which is how a free request comes back as somebody else's model.
5. Run the full bank in the background with `--repeats 3` for candidates and 1 for frontier references, sharing one `--root`. Price the run from the smoke rows first and gate it on the shared OpenRouter key: `GET /api/v1/auth/key`, reporting `limit_remaining` with units, printing only `label`/`limit`/`limit_remaining`/`usage_weekly` and never the key value. A run stopped for budget is a reported blocker, not a failed run: stop at the guard rather than burn the cap, and never raise it. Before wiring a new arm, state a cost ceiling for the whole run (repeats included) in the run plan and price it from the smoke rows rather than the per-call rate: an agent arm resends the growing history every step, so tens of calls per task on a metered key dominate the bill. Arms on a model Deep has banned are refused by a guard at the driver entry (`hermes_lane.sh` refuses the banned slugs before spawning): keep the guard and change the arm's model list, never the guard around the model. Report tier verdicts, PASS/FAIL per task, and cost with explicit units from the `models.json` price. Reports follow house rules: no em dashes, no en dashes. State each model's rows and repeats alongside its numbers: a frontier reference run once and a candidate run three times are not the same evidence, and a table that shows means without run counts invites a comparison the data cannot support.

## Pitfalls

- macOS has no `timeout` binary: `timeout 600 python3 run.py ...` dies with `command not found` and creates no results root. Run the smoke bare under the terminal tool's own timeout.
- On `judgment-appraisal` the prompt forbids computed figures, so derived attainment percentages (87.5, 125) are a genuine instruction miss, not a checker defect. `abm-plan` flags list ordinals (`1`, `2`) on every model, so its 0.89 ceiling is shared and does not separate candidates.

- A run can come back clean from the wrong model: Hermes falls back to another provider on a 429/403, and a `:free` OpenRouter route whose driver dropped the auth header is answered by the proxy's own model with HTTP 200. Never score a row without comparing `_usage.json` model to the row's key (`run.py` marks a mismatch ERR), on every row's first run rather than once per setup; mechanism in `references/model-drivers.md`.
- The default Hermes profile makes models append notes to Deep ("Not covered: ...", word counts, decision cards). Checkers that count words or numbers then penalise the model for obeying house rules. Score only the text between `<answer>` tags (`run.deliverable`); the v1 footer did not ask for tags.
- Judge on the tier table, never on one overall mean: one failed tier hides inside a high average, and the efficient pick per tier means pass on every run first, then cheapest list price, then fastest. State repeats beside every score (a reference run once and a candidate run three times are different evidence), split basic (tiers 1 to 2) from major (tiers 3 to 4) cost, and mark a hosted full-precision score as a stand-in for the 4-bit file you would actually load.
- A cheap model that passes routine tiers and fails the heavy ones is not a global swap: route by tier, keeping the failing tier on the subscription model. An overall mean hides exactly the split that decides the routing, so report the tier table first and the average second.
- Judge scoring against a stale judge run silently mixes two judges. When the judge changes (a selftest fix, a prompt or rubric edit), re-score every row into a fresh `--root` and compare roots, never old rows against new ones; a table spanning two judge versions is two measurements presented as one.
- Memory pressure contaminates a measurement: with swap nearly full, a local load measures thrashing instead of the model's speed, and the disk it borrows for swap can be the disk the download just filled. Gate any local load on free memory first (`open-model-runnability-probes`).
- A shared OpenRouter key at its weekly cap still serves `:free` endpoints, but free upstreams rate-limit and may log prompts: proxy signal only, fictional fixtures only.
- Exempt the numbers the task itself demands from any "no invented numbers" check. A confidence score the prompt requires is not an invented number, and a checker that fails its own good sample is broken, not strict. Strip identity tokens the page must carry (brand names like `LakeB2B`, URLs, versions) before collecting numerals: a name containing a digit trips an allowlist and marks down every model for a false positive.
- A stitched full-page screenshot renders sticky and fixed elements at their scroll-time position, so a header appears to sit on top of mid-page content. Before logging an overlap or occlusion defect, re-shoot that section in a normal viewport scrolled to it; only a defect that survives the viewport shot counts. Apply the same rule to hidden skip links, which are off-canvas until focused and read as stray elements in stitched captures.
- The harness's `_usage.json` covers one lane's own accounting, not the key. Price a run from `session_model_usage` joined to `sessions` on `session_id`, filtering on each run's results directory in `cwd`: that catches arms launched by wrapper scripts or by hand, and it is the only view of what the shared key actually spent in the window. Reconcile that local sum against `usage_weekly` from `/auth/key` and report any gap as unattributed, since other consumers share the key.
- A model driven through a subscription CLI meters in plan units (Codex credits) while the same run prices differently at API list rates. Report both beside the wall time: the two meters rank models differently, and a lane decision made on either one alone is made on half the cost.
- When a check passes standalone but fails inside `score()`, diff the actual bytes of the written file before re-deriving the logic. Layered writes can double-escape backslashes in regex literals, so the harness runs a different pattern than the one you tested.
- Expected values you wrote into the prompt (reference implementations, hidden test expectations) can be wrong. Verify each by independent calculation before blaming a model for missing it.
- A task whose checker only rewards the good sample and never flags the bad one reports every model as 1.00; the pass column then measures nothing. Run `--selftest` and confirm the bad sample scores at or below the threshold before trusting any row.
- An Anthropic-compatible endpoint returns thinking blocks alongside text. When `content` comes back empty on HTTP 200, read the raw body before concluding anything.
- An ad-hoc probe (a throwaway harness written outside the suite) needs three guards or it reports the wrong winner. **Empty output with `finish_reason=length` means the cap was too low, not that the model failed**: hidden reasoning spends the output budget, so re-run that row with a much larger `max_tokens` before scoring it. **Identical prompts hit provider cache**, so latencies of 0.2s against 30s are a cache artifact: put a random nonce in each request before timing anything. **A small sample cannot crown a replacement**: only say a candidate beats the incumbent when it passed every run of the task where the incumbent also passed, with the run counts beside both.

- **A bench whose output is an ordered fallback list in production code must write its evidence into the code.** Bench the real endpoint with the inputs production actually sends (the messy ones, not clean fixtures), report the task's accuracy metric beside p50/p95 latency, and put those numbers in a comment on the ordered list. An unannotated fallback order reads as a guess, so the next reader cannot tell a measured first choice from a default, and will "fix" it back.

- **A 1 to 10 vision rubric does not rank design work.** On the showcase bake-off it scored every page between 8.2 and 8.4, including the two Deep rejected as plain, so absolute scores are not evidence of a winner. Rank pages with a pairwise forced choice (two screenshots, "which would you ship and why") plus a structural fingerprint (count the components the house kit provides). Treat Deep's own pick as the verdict and the vision pass as defect-finding only.
- **An agentic build eval must put the absolute output directory in the prompt.** `hermes -p <profile> chat` tools start in the profile's `terminal.cwd` (the vault root on `default`), not the shell's cwd, so "work in the current directory" sends parallel runs to one shared file: they overwrite each other, a model may even merge a rival's edits, and the vault root collects stray files. Template the path into a per-run copy of the brief, then confirm each run's files landed in its own directory before scoring. Worked example: `Efforts/LLM Bake-off/Showcase Page Eval v1/run.sh`.

## Ad-hoc build eval: one task, models side by side

When Deep names N models and one build task (a landing or showcase page), skip the suite harness and run a self-contained eval folder under `Efforts/LLM Bake-off/<Name> Eval v1/`:
1. `brief.md`: the task, fictional client data, and an explicit `no invented numbers` rule with the facts the page must state, so the checker's allowlist and required strings come from the brief, not from reading the outputs.
2. `run.sh <label> <provider> <model>`: one parameterized runner; template the absolute per-run output directory into each brief copy (see the output-directory pitfall below). Launch all runs in parallel with `wait`, capture wall time and exit code per run to `runs/<label>/_run.json`.
3. `score.py`: deterministic gates, and calibrate it exactly like a suite checker before trusting it: hand it a known-good page (expect full marks) and a deliberately faulted page (expect clear failures). Fix the checker on a false positive before scoring any model; never mark a model down for the checker's bug.
4. Screenshots at 1440 and 390 into `runs/<label>/eval/`, then a vision model as design judge with **model names kept out of the prompt**; score named dimensions (hero, hierarchy, brand fit, metrics, scroll beats, polish) so the comparison is structured. Note honestly that the judge still sees which page is which when you read results.
5. Cost three ways: wall time, the plan's own meter (credits from `_run.json`), and API-list equivalent from session telemetry. End with run count beside the verdict: one run per model is a signal, say so, and name the skipped work (repeats, second judge, components the production lane would use).

Worked example: `Efforts/LLM Bake-off/Showcase Page Eval v1/` (`brief.md`, `run.sh`, `score.py`, `results.md`).
