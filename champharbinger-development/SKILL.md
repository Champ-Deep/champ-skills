# ChampHarbinger development

## When to Use

Any card touching this repo: a ChampHarbinger bug, feature, route, cron or job
scheduler change, domain or mailbox behaviour, or a question about what state
production is actually in. Pair with `systematic-debugging` for the general
root-cause method; this file carries the repo's own facts and traps.

ChampHarbinger is Deep's cold-email sending platform: Next.js on Cloudflare Workers, D1, Hyperdrive, sending through the InboxKit and OpenMail providers, live at `champ-harbinger.deep-ae0.workers.dev`. Feature work happens on branches with PRs; Deep merges and deploys.

## Repo identity

- Canonical checkout `/Users/deep/repos/ChampHarbinger-cf`. Per-branch worktrees appear as `/Users/deep/repos/ChampHarbinger-cf-<branch>`; run `git worktree list` before creating one so concurrent lanes do not collide, and branch off `main` unless a card says otherwise.
- Never trust a folder name: `git remote -v`, `git fetch origin`, then compare `HEAD` against `origin/main` before planning against "the local codebase".
- No em dashes in any output, including commit messages, PR bodies and UI strings. Before every commit run `git diff --cached | grep '^+' | grep '[–—]'` on its own (it exits 1 when clean, so never chain it with `&&`): only an added line can violate the rule, and one second of grep beats re-reading the diff by eye.

## Where production truth lives

- The dashboard is a cache viewer. Health, limits and capacity screens read snapshot tables and fail closed, so an empty table renders as an alarming failure state. Empty means "never checked", not "failing".
- Answer "is X actually true in prod" with a read-only SELECT against the live D1 for that worker, never from a screenshot or from what the code ought to do.
- "Is it wired?" and "is anyone using it?" are two different reads. For wiring, `npx wrangler secret list` on the prod worker name returns the secret NAMES only (never values, so it is safe to print): a feature built and unit-tested in code still cannot work in prod when its provider credentials were never pushed, and the UI renders the dead button anyway. For adoption, count rows: `auth_users`, `team_members` (an empty table means the launch never happened), and `sent_emails` grouped by recipient domain, since every send to an address the app's own owner holds proves only that bytes moved, not that a prospect ever received mail. Diff the `jobs` table by schedule name across the gap when something "stopped working", and read `mailbox_connections` before assuming a mailbox row exists.
- The provider console (InboxKit / OpenMail) is the authority for domain DNS status and inbox credentials. Any Harbinger message that names a specific check must be backed by a row that check wrote; otherwise the message is inventing evidence.
- You have no session in production. Anything that needs Deep's auth (an import button, a manual re-check) gets an endpoint he can call while logged in; do not try to fake it.

## Cron: the in-house `d1-boss` scheduler

- `src/lib/jobs/d1-boss.ts`. Not pg-boss: runs live in the D1 `jobs` table and each scheduled run carries a singleton key `cron:<minute epoch>`, which makes a duplicate enqueue for the same minute a harmless no-op.
- Schedules resolve to per-minute slots. A schedule pinned to one minute (an hourly at `:07`) is the only kind a single missed or throwing tick can silence for a whole period, while interval schedules (every 5 minutes) keep running. That makes an outage look selective: if some jobs ran and others did not, suspect the slot bookkeeping before the job's own code.
- Correct behaviour is: walk every minute since the last successful tick (bounded, one hour), enqueue each matching schedule, and advance the stored minute only after the sends succeed. Marking the slot first turns one transient D1 error into a permanently lost period.
- Expect a one-time burst of every hourly job on the first deploy that adds catch-up.

## Build loop

1. `source ~/.nvm/nvm.sh && nvm use 24`, then `pnpm` for everything (repo tooling is pnpm).
2. Type: `pnpm exec tsc -p tsconfig.json --noEmit`. Per-file tsc is deliberately skipped by config, so only the project-wide run counts as evidence.
3. Lint: `pnpm exec eslint <touched files>`. Baseline carries pre-existing warnings (unused `_`-prefixed parameters): zero new problems, no mass cleanup of old warnings.
4. Test: `pnpm exec vitest run <touched suites>`, then the full suite before claiming green. Unit tests mock `@/db`, so they cannot touch prod state.
5. Report only gates whose command output you ran in that same turn.
6. When the full suite reports timeouts in files you did not touch, check `uptime` first: this suite pays a per-test setup cost, so a loaded machine inflates timeouts across unrelated files. Re-run the named files alone, and let CI on a clean runner arbitrate the final verdict. State in the PR body that the local run was noisy and CI is the gate, rather than re-running the whole suite until the box quiets down.
7. `vitest.config` restricts `testMatch` per project, so a path-restricted run can match zero test files while other files in the same command do run. Read the `Test Files` count of every shard and require it above 0 before quoting a pass number: a shard that matched nothing is an unrun shard, not a green one.
8. Poll `gh pr view <n> --json statusCheckRollup` for the conclusions (not `gh pr checks`, which reports `pending` for jobs that already finished) and require `mergeStateStatus=CLEAN` before merging.

## Shipping

- Stage by explicit path (`git add <file> <file>`), never `git add -A`, `git add .` or `commit -a`: worktrees here pick up other lanes' files, and one round swept another card's untracked doc into a scoped PR. Before every handoff, compare `gh pr view <n> --json files` with the card's changed_files and SCOPE line; any extra path is a defect.
- Structured commit body (why / what / proof), then `gh pr create` with what is in, what was verified, and what is explicitly not proven. Never push to `main`, never merge, never delete a superseded branch.
- Production deploy (the repo's Cloudflare deploy script plus its smoke checks) happens only after Deep picks a decision card: a `needs_input` kanban block with options and your recommendation first, deploy action named as the recommended option. Stage it and say where it is staged.
- Keep contract PRs (API routes other cards depend on) draft until Deep says ship them; branch later fixes off `main` so each PR stays independently mergeable.

## Sending gates (who can actually receive mail)

- `deploy/cloudflare/worker.ts` pins `PILOT_STRICT_SENDS=1`: only pilot campaigns send. A pilot campaign's `pilot_campaigns.transport` decides: `record` transmits nothing (Inbox says "Recorded only. Not sent."), `live_test` only the 10-address allowlist, `live` any recipient that clears approval, country, pause, reply and bounce gates. worker.ts sets `PILOT_DEFAULT_TRANSPORT=live` (Deep, 9 Nov), so only campaigns created after that are live. Before answering "can the team send", read `transport` for their campaigns.
- Every new channel path that sends for a pilot campaign (voice brief, LinkedIn, WhatsApp) must load the pilot policy (`loadPolicy` in `src/lib/pilot/send-gate.ts`) at dispatch time and honour it like email does: `record` transmits nothing, `live_test` only reaches a person whose email is on `testRecipients` (the allowlist holds emails, not phone numbers or profile URLs), and a `runState` other than running or idle holds the send. A human approval or a flag that lifts `PILOT_STRICT_SENDS` (`briefApproved`, `isTest`) is not the policy: without the policy read an approved item in a `live_test` dry run reaches a real phone. Test each of the three cases with zero provider calls.
- Daily cap, bounce breaker and throttle count by sending address across all users (teammates share an imported inbox). Never re-add a `clerkUserId` predicate there.
- Replies go through the same guardrails as cold sends: `outreach-sender.ts` calls `runSendGuardrails` on the pinned mailbox for `isReply` sends, so any cap you lower (a warm-up 0, a ramp step-down) silences answers to people who replied unless you exempt them. Ramp and domain caps are cold-send caps; test a reply against a cap of 0.
- A shared cap split into per-mailbox shares (the domain-wide 100) is enforced one mailbox at a time, so every mailbox must compute the split from the same keyed view (share and sort by lowercased address, never by a row id for self and an address for peers), or remainders land on several mailboxes and the sum overshoots. Test the sum of each mailbox's own lookup, not one mailbox's view.
- An optional service wired on by default (a bundled container behind `appEnv()` defaults) still needs a documented off value that its client maps to `not_configured`: a blank value falls back to the default, and `PERSON_RESEARCH=off` kills all person research, so without it the only off switch is a code deploy. State its per-contact cost in the PR: person research runs once per contact, in sequence, inside `pilot-run` (`expireInSeconds` 3600, `retryLimit` 0) and inline in Quick Send, so seconds and cents per call multiply by the campaign size.
- A new env var must land in three places or the app never sees it: `deploy.sh` `OPTIONAL`, `worker.ts` `APP_ENV`, and `env.env.example`; `src/lib/deploy/cloudflare-env.test.ts` checks the first two agree.
- lakeb2b.com, engageprob2b.com and spanglobalservices.com are on SURBL abuse (`dig +short <d>.multi.surbl.org` returns 127.0.0.64). No links to them in any draft or signature.
- Admin: re-inviting an existing member's email is the password reset (new set-password link); disable ends sessions at once.
- Draft guardrail `hasLowFrictionAsk` judges the last two sentences ending in . ! or ?; the prompt appends the profile signature, so before #136 any multi-line signature sent every draft to the generic fallback. When drafts come back as "Quick note" / GENERIC-SAFE FALLBACK, read the `Rules the AI drafts broke:` suffix in `ai_reasoning`.
- A Quick Send to a freemail address (gmail) has no company to research, so no citation, so `approveDraft` refuses it (`research_incomplete`, no waiver). Live tests go to a company-domain address.
- The send window is recipient-local 08:00 to 18:00; an India recipient tested in Deep's evening is approved and deferred to 08:00 IST (`outside_send_window` 409 from send-now is the gate working). A `live_test` campaign whose recipient is on the allowlist is exempt: the pilot gate marks those decisions `test: true` and `sendClaimedDraft` skips the window for them, so an owner-approved test need not wait for morning. Cold recipients keep the window; never widen it for them.
- "Is sending actually working?" is answered by one mail, not by the state you can see: send a real message from a production sender address to a real address Deep owns, then read the row back from `outreach_emails` and quote its `id`, `from`, `to`, `status` and `error`. Sending the test to a mailbox this app itself hosts proves the pipeline moved bytes, not that a third party accepted and delivered it, so send at least one copy to a domain Harbinger does not control. Report the exact address the copy went to: a test received on one address and "missing" on another was never missing.
- Driving prod as Deep: `browser_exec(local=True)` has his session; fire long calls (`/api/quick-send` streams 30 to 60 s) without awaiting in `js()` (5 s eval cap) and read `quick_sends.stage` from D1. Pilot draft actions are POST `/api/pilot/<campaign>/drafts/<draft>` with `action` approve (needs `versionHash`), edit, reject, redraft.

## Prod reads and smoke

- Read-only D1: `CI=1 npx wrangler d1 execute champ-harbinger --remote --json --command "<select>"` from `deploy/cloudflare` with `CLOUDFLARE_ACCOUNT_ID` set. Column names: `jobs.created_on`/`state`, `mailbox_connections.created_at` (ms epoch). Take the account id from `npx wrangler whoami` and export it: with the variable unset the same read failed with error 7403. For "is channel X really in use", count rows: `outreach_messages` and `channel_accounts` hold voice, WhatsApp and LinkedIn (empty means never used in production, whatever the code says), `sent_emails` holds email, `kg_nodes`/`kg_edges`/`kg_episodes` the graph, `signals`/`signal_results` the signals engine.
- A readback that ties reply evidence together must key on the contact (`campaign_people_id`), never on the original draft's `enrollment_id`. Pilot drafts are saved with no `enrollment_id` (`src/lib/pilot/default-deps.ts` calls `saveDraft` without one), `haltOnReply` (`src/lib/aisdr/respond.ts`) halts every running enrollment of the contact by `campaign_people_id` (and the same person in the owner's other campaigns), and the answer draft stores only `haltedEnrollmentIds[0]`. A join on `original.enrollment_id` reads FAIL on a pilot reply that worked. Answer drafts are the `email_drafts` rows whose `ai_reasoning` starts with `[reply intent:`; there is no `pilot_drafts` table.
- Print or match status and disposition values from the source enums, never a hand list: `CALL_DISPOSITIONS` in `src/lib/channels/voice/disposition.ts` (connected is the fallback and the most common) and `OUTCOME_STATUS`/`DISPOSITION_STATUS` in `src/lib/channels/voice/agent-call-report.ts` (answered, delivered, no_answer, interested, not_interested, failed). A guessed list turns a normal answered call into "other".
- Before trusting a readback script's SQL, build an in-memory SQLite from `db/migrations/*.sql` (split on `--> statement-breakpoint`) with `node:sqlite` and prepare every query: a hand-written test schema hides wrong column names.
- `deploy/cloudflare/smoke.sh https://champ-harbinger.deep-ae0.workers.dev` needs the base URL argument; without it it exits 1 with a usage line.
- smoke.sh takes its D1 name from `wrangler.jsonc` (line 9), not from the URL or `CF_D1_NAME`, so pointing it at a staging or preview worker still mints, accepts and deletes its throwaway invite in the PROD D1. Until the script honours `CF_D1_NAME`, never run it against a non-prod URL without a copy of `wrangler.jsonc` whose `d1_databases[0]` names the staging D1, and after any such run read prod `auth_invites`/`auth_users`/`auth_sessions` for `smoke-%@harbinger.test` rows.
- Deploy from a clean detached worktree of `origin/main` with `ENV_FILE=<canonical checkout>/deploy/cloudflare/env.env`; the container rollout wait takes 15 to 25 minutes, so run it in the background.
- Run `npx wrangler whoami` before promising anything that needs a deploy or a D1 read, and again just before the deploy: the OAuth session on this Mac can die mid-session ("You are not authenticated" while the stored expiry is still in the future). Only Deep can restore it with `npx wrangler login`: the Cloudflare login page sits behind a bot challenge, the Hermes browser copy is not signed in and no login is stored. Card it at once as a `needs_input` decision with that one command, because every later step (merge value, deploy, seeding, prod reads) waits on it.
- Voice keys reach production only through a deploy. `DIAL_API_KEY` set in `env.env` does nothing until `deploy.sh` pushes it, so "the key is in env.env" is not "production can dial". Prove it with `npx wrangler secret list` after the LIVE line.
- A route the worker reaches through `postInternal()` must be listed as public in `src/proxy.ts` and verify the worker secret itself. Without the entry the job dies on a silent 401. `src/proxy.test.ts` enforces this; add the new path to its required list in the same change.
- `signals.slug` is unique across all tenants. Code that looks a signal up by a fixed slug must also require `isBuiltin` true and `clerkUserId` null, and the user-facing creator must refuse that slug prefix, or one tenant can hold the slug, collect every tenant's `signal_results` on their row and delete them by cascade. That includes an insert `onConflictDoNothing` followed by a select by slug (a self-seeding catalog): the conflict silently keeps the tenant's row. The chat tool `createSignal` (`src/lib/tools/signal-tools.ts`) takes any slug, so the prefix refusal goes there too, not only in `/api/signals` (which appends a timestamp).
- A job that self-attaches `campaign_signals` rows must read them back: the scan runs only the types whose row is `enabled` for that campaign, or the attach is decorative and the per-campaign off switch does nothing. Test it by disabling a row and asserting no result of that type is stored.
- A keyword signal classifier is a precision heuristic. Before shipping it, run the negatives that share its verbs ("raises prices", "raises concerns", "joint venture" all typed as funding in PR 143): a mis-typed weight 3 item tops the account ranking and is cited to the prospect in the draft. A currency amount next to the verb is not round context either: contracts, deals, revenue, guidance, acquisitions and price changes all carry amounts ("secures $50M contract", "raises guidance to $5B", "closes acquisition for $200M", "raises prices by $5" all still typed as funding after the first fix). Test a matrix of amount-bearing non-funding headlines, not only the bare-verb ones. A deny list of nouns between verb and amount does not close it either: "raises <anything> to $N" (wage, bid, capex, buyback, EPS estimate, fees, spending) passed the second fix, 12 of 16 fresh negatives. Require the amount directly after the verb ("raises $20M", "raised Rs 200 crore") and apply the deny list (contract, deal, order, tender, revenue, guidance, price, dividend, stake, charity) to the whole headline. Reviewers: always add negatives the lane was never shown, because a lane fixes exactly the list it was handed.
- `isTest` on a `ChannelMessage` is not a trust signal: the chat agent's `callContact` sets it for any number with no contact record. Gate a relaxed rule on a flag only the allowlist-checked routes set (`approvedNumber`), never on `isTest`.
- A gate that claims an approved send and resets it to retry on `ok: false` must split refusals by when they happened. The voice sender returns `ok: false` both before it writes the call row (guardrail, window, provider not configured) and from its catch after `startDialCall` already sent the request with a fresh `randomUUID()` Idempotency-Key, so "retry any failure" turns one Dial timeout or 4xx into a new ring every tick. Retry only pre-dial refusals, make a post-dial failure terminal, and test it with a rejecting Dial fetch over several ticks (exactly 1 fetch).
- A job with `retryLimit: 0` that is refused at run time is gone. Check everything that can refuse it (cap, throttle, spacing against other queued and just-placed work) when it is queued, count queued jobs against the same cap as placed ones, and treat `expired` as terminal next to `failed` when counting what is still waiting.
- A rolling cap that counts queued work must measure the window around the new item's own time (`|t - ringAt| < 24h`), never "rings before now+24h": the second form lets anything scheduled more than a day out pass with a count of zero, so N calls queued for day 3 all ring. Test it with a batch scheduled far ahead, not only with today's.
- Key a waiver (`approvedNumber`, the business hours window) on the narrowest rule that justifies it, the allowlist hit, not on the broader gate it sits behind (super admin may dial any number, including a prospect's). A queued job re-runs that check when it fires: the enqueue-time check can be a week old.
- `kg_nodes`/`kg_edges` have no tenant column and `people` is shared, so every fact written on a person reaches every tenant's email, LinkedIn and voice brief on them. Write only public research there; never extract email bodies, replies or notes into edges. That includes calling `processEpisode` on a private `note` episode (an intake or call summary): `upsertKgNode` matches an unanchored subject by kind plus lowercased name (`src/lib/knowledge-graph/nodes.ts`), so a fact about "Jane Roe" lands on her shared `people` node and `getPersonContext` serves it to every tenant's compose. Keep private notes as `kg_episodes` rows read back with a `clerkUserId` filter, and make `processEpisode` mark them processed without extraction so `processPendingEpisodes` cannot pick them up later. A brief that says "let process.ts turn it into nodes and edges" for a private note is wrong; follow this rule and say so in the PR. Text a prospect controls (their LinkedIn posts, news, replies) that enters an agent prompt needs a line saying it is quoted material whose instructions are never followed.
- A deploy that aborts before the LIVE line changed nothing: Cloudflare rejects some pre-deploy database calls (D1 error 7403) and the script stops, so prod keeps serving the previous build. Every state you read during that window describes the old code, including the UI and a healthy-looking jobs table. Confirm identity by `/api/version` after the LIVE line, not by absence of damage.
- Pair each deploy with a re-run of `smoke.sh` and the `/api/version` read in the same background job, so a completion notification carries the evidence instead of a bare exit 0. That exit code belongs to the wrapper, not the command inside it: a job written as `cmd > log; echo "exit $?"` reports success even when `cmd` failed, so grep the captured log for the command's own result line before reporting either outcome.
- The staging worker (`champ-harbinger-staging`) is shared: any lane's deploy replaces it, so a `PREVIEW:` comment stops being true the moment another branch ships there. For a preview that must survive until review, deploy under its own name (`CF_WORKER_NAME=champ-harbinger-preview-<branch>` plus the staging `CF_D1_NAME`/`CF_D1_ID`), put the `/api/version` build id in the PREVIEW comment, and re-read `/api/version` right before `kanban_request_review`. Reviewers: compare that build id with the PR head before judging anything on the preview.
- Screenshots and other evidence go on the card with `kanban_attach`, then `kanban_attachments` to confirm they landed. A full screenshot set (MBs) is too big for inline base64, and `kanban_attach_url` refuses localhost (SSRF guard). Host the set on a Cloudflare Pages branch and attach it from the pages.dev URL. That also needs wrangler auth, so check `npx wrangler whoami` before shooting.
- Copy shots out of the profile cache dir into the card workspace the moment they exist. The cache is pruned after 24 hours. Paths listed in `kanban_request_review(artifacts=...)` from a profile cache dir are not copied, and that dir is pruned after 24 hours.

## Proving the review-to-send path end to end

- Pilot draft actions are POST-only on `/api/pilot/<campaignId>/drafts/<draftId>` (PATCH answers 405): `approve` (bound to the versionHash the reviewer saw), `edit`, `reject`, `redraft` (optional `country`). Each takes a JSON body. Drive them from Deep's logged-in local browser session rather than reconstructing shapes from route code.
- The reviewer's queue is `/inbox/<campaignId>`; read its JSON from that same session to see what a teammate would actually see.
- `redraft` is how you re-run research after fixing a contact: it clears the stuck draft and queues a fresh one with readiness recomputed.
- Reject test drafts you do not want sent, and say in the reason why, so a leftover draft cannot be approved later.
- After any write, read the row back from D1 (`email_drafts` with its `pilot_meta`, plus `transport` on `pilot_campaigns`) before claiming the path works; a 200 only proves the route ran.

## Pitfalls

- Never write a status or guardrail message that asserts a check which did not run. Distinguish "has not been checked yet" / "was last seen X" / "is X": the fail-closed path is where a user reads the loudest claim, and a wrong claim there sends them fixing DNS that was fine.
- Writing a child row does not write derived caches (mailbox import does not populate domain health). Refresh derived state in the same request, or the new record looks broken until some background job happens to run.
- The terminal display masks phone numbers (`+141****0123`). Never copy a literal from tool output into a test or fixture: read the value from the file in code, or the mask lands in the repo and the route rejects it as an invalid number.
- Repeated blind `patch` calls on a large file compound into structural damage; once two edits in a region misfire, read it and rewrite the enclosing function in one write.
- Send-now from any review surface is two writes: PATCH `reviewStatus: "approved"` (send-now 409s on anything else), then POST `/api/outreach/send-now`. When the second write fails, the first one still stands: the draft is approved and the scheduler sends it at `next_send_at`. Either PATCH it back to `pending` before showing it as reviewable again, or refresh so it shows as approved. Test the failure path's writes too, not only the happy path's, because a card that shows "Ready for review" over an approved row sends mail the user was just told did not go.
- A missing value must not render as a zero on `src/components/ui/gauge.tsx` (21st Gauge 1757). With `value={0}` the primary arc stays at opacity 1 and `strokeLinecap: "round"` paints an accent dot, so a null confidence looks the same as a real score of 0. For null, draw no primary arc (`primary="transparent"`, or leave out the Gauge) and use a track that shows in dark theme (`var(--border)`, not `var(--muted)`). Then assert in a test that the primary circle is not painted. An aria-label check alone passes while the dot still shows.
- "Drafts can't be approved" is usually a gate working as designed, not a broken button. `approveDraft` (`src/lib/pilot/review.ts`) refuses on `readiness.state === "blocked"` (for example, jurisdiction when the country is unknown), on empty `citations` (research_incomplete, with no waiver), and on lint hits. Readiness is stored in `pilotMeta` when a draft is composed and is never recomputed. Fixing the contact therefore means rejecting the draft and redrafting it (the `redraft` action on the pilot drafts route), not editing the draft. Read the live `/api/pilot/<id>/review` from Deep's logged-in local browser before touching code. Two things misread that gate as a bug: readiness is a snapshot, so a contact fixed after compose still fails until redraft; and a consumer-domain recipient (gmail and the like) has no company to research, so citations stay empty forever. Test the approval flow with a company-domain address or you will chase a gate that is working.
- `email_drafts` has three insert paths, despite the comment in `save.ts` calling it the only one: `email-composition/save.ts`, `aisdr/respond.ts` and `channels/voice/post-call-email.ts`. A field stamped on drafts, such as attribution or a recipe, must reach all three, and each one needs its own test.
- `sent_emails.delivered_at` is written only by the provider webhook route (`api/email/track`). SMTP mailbox sends never get it, so any rate built on it reads as zero delivered. Use "sent minus bounced" as the denominator instead.
- `suppressions` is one global table with no tenant column. Any export must be scoped to addresses the team itself emailed. Any import suppresses those addresses for every tenant, so make that a policy decision card, not an implementation detail.
- The DB is D1 behind pg-style builders (`db/dialect.ts`). `pnpm db:generate` writes `db/migrations`, while `db/migrations-postgres` is frozen history. SQLite has no sha256, so a content-hash backfill has to run in code (lazily on first read or write), not in migration SQL.
- Every raw `sql` fragment runs on SQLite, not Postgres: `body || ${json}::jsonb` is a syntax error on D1 (`unrecognized token: ":"`), and without the cast `||` is string concatenation. Merge a JSON key with `json_set(coalesce(col, '{}'), '$.key', ?)` as `src/lib/sequencing/guardrails.ts` does; `->>` is fine. A `.catch(() => undefined)` on that write turns the error into silence, and the chainable db mocks pass any SQL, so a test that counts `db.updates` proves nothing. Execute the fragment on an in-memory SQLite built from `db/migrations` (`node:sqlite`) in the test, or render it with drizzle-orm/sqlite-core's `SQLiteSyncDialect` and run it there.
