# Visual Report Builder

> Documents that happen to be built in HTML.

This skill produces single-file, self-contained HTML pages that present data, decisions,
and strategy with magazine-editorial quality. The output is a document you can open in any
browser, share as an attachment, or host on a static server. No build tools. No frameworks.
No dependencies beyond Google Fonts and (optionally) Chart.js from CDN.

The core philosophy: **skimmability is the product.** A reader should understand the
score within 3 seconds of opening the page, grasp the structure in 10 seconds, and
find any specific detail within 30. Every design decision serves this goal: typography
creates hierarchy so the eye knows where to land, color encodes meaning so the brain
doesn't have to decode it, and layout groups related information so context is never
more than a glance away. If a visual element doesn't make the data clearer, the
structure more navigable, or the story more scannable, it doesn't belong.

## The Skimmability Contract

Before diving into specific design patterns, understand what this skill optimizes for.
The reader of these reports is busy: a CEO scanning before a board meeting, a sales
lead checking pipeline between calls, an investor reviewing 12 decks in an afternoon.
They will NOT read your document top to bottom. They will scan it.

**The 3-10-30 rule:**
- **3 seconds:** The reader sees the hero stat strip and knows the headline numbers.
  Revenue, win rate, deal count, status. No scrolling required.
- **10 seconds:** The reader scans the section headers (01, 02, 03) and grasps
  the document's structure. They know what chapters exist and can jump to any one.
- **30 seconds:** The reader finds a specific data point. The combination of
  numbered sections, color-coded metrics, and visual patterns (bars, charts, grids)
  means nothing is buried in prose. Every fact has a visual home.

If your report fails any of these benchmarks, redesign. The visual treatment is not
decoration. It is the user interface for understanding.

## The Five Design Principles

These aren't rules to follow mechanically. They're the thinking behind why the output
looks the way it does. Internalize them, then design freely.

### 1. Editorial, Not Corporate

The difference between a magazine spread and a PowerPoint export is intentionality.
Every element has a reason. Whitespace is generous. Typography does heavy lifting.
The page should feel like it was designed by someone who cares about craft, not
generated by a template engine.

**What this means in practice:**
- Use a serif display font for headlines (Fraunces, Playfair Display, DM Serif Display).
  Serifs signal authority and editorial intent.
- Use a clean sans-serif for body text (Montserrat, Inter, DM Sans). This is the
  workhorse. Readability above all.
- Use a monospace font for data labels, timestamps, section numbers, and metadata
  (JetBrains Mono, IBM Plex Mono, Space Mono). Mono signals "this is factual."
- Headlines should be large enough to feel like a statement. `clamp(38px, 9vw, 88px)`
  for h1. Not shouting. Confident.
- Use italics in headlines to create visual rhythm. One word in italics breaks the
  monotony and draws the eye: "A merchant bank, *in formation.*"

### 2. Numbers Are Heroes

In a report, the most important content is usually a number, a percentage, a date,
or a status. These should be the largest, most visually prominent elements on the page.
Not buried in paragraphs. Not crammed into table cells.

**What this means in practice:**
- Stat strips: large numbers (28-44px display font) with tiny labels underneath.
  Grid them in a row. Separate with hairline borders or gaps.
- Use color to encode meaning: green for "ready/positive", gold for "notable/target",
  red for "urgent/risk", purple/brand-accent for "primary metric."
- Progress bars and gauges for completion/temperature/progress. Visual, not textual.
- When you have 3-7 key metrics, always lead with a stat strip right after the hero.
  The reader should know the score within 3 seconds of opening the page.
- Numbers that arrive on scroll count up to their exact stated value; the final value
  is written in the HTML so exports and no-JS readers see it.

### 3. Sections Tell a Story

Each section of the page is a chapter. It should have a clear beginning (what are we
looking at?), a middle (the data), and an implication (so what?). Sections are numbered
and labeled so readers can navigate and reference them in conversation: "look at section 3."

**What this means in practice:**
- Section headers are one mono eyebrow line: a two-digit number (`01`) then the topic
  (`The setup`, `The deal`, `Next steps`). No section sign (§) and no pill outline around
  the topic: Deep reads the `§ 01` pill as an AI-generated tell (16 Oct 2026), and
  executive-one-pager and b2b-growth-showcase already ban it.
- Below the header, a serif h2 states the section's thesis in 3-6 words, with one
  word in italics: "The capital *stack.*"
- The section body uses cards, grids, bar charts, tables, or split layouts. Never
  plain paragraphs of body text. If the data can be visual, make it visual.

### 4. Dark by Default, Brand by Choice

Dark themes reduce eye strain for documents people revisit. They also make data
visualizations pop (Chart.js charts look dramatically better on dark backgrounds).
But the skill adapts to any brand palette.

**The theming system:**
- All colors live in CSS custom properties on the root class.
- When a brand skill is loaded (LakeB2B, SPAN, Ampliz, Champions Group), pull the
  primary and accent colors from those guidelines and map them into the custom
  property system.
- The dark palette is the default. For brands that require light backgrounds, invert
  the surface/text hierarchy while keeping accent colors consistent.
- If no brand skill applies, use a neutral dark palette with purple as the accent.

**Minimum custom properties for any report:**
```css
--bg:           /* deepest background */
--surface:      /* card/section background */
--surface-2:    /* elevated surface */
--line:         /* borders, dividers */
--text:         /* primary text (high contrast on bg) */
--text-2:       /* secondary text */
--text-3:       /* tertiary text, labels */
--accent:       /* primary brand accent */
--accent-glow:  /* lighter version for gradients/highlights */
--positive:     /* green, for "good" states */
--warning:      /* gold/amber, for "attention" states */
--negative:     /* red, for "risk" states */
```

### 5. One File, Zero Friction

The output is a single `.html` file. No CSS files. No JS bundles. No build step.
Someone can double-click it in Finder and it opens perfectly. Someone can email it
as an attachment. Someone can drop it on Netlify and it's deployed.

**What this means in practice:**
- All CSS in a `<style>` tag in `<head>`.
- All JS in a `<script>` tag before `</body>`.
- Google Fonts via `<link>` (these work offline after first load).
- Chart.js from CDN if charts are needed (the only external dependency).
- Scope all CSS under a root class (`.report-root` or project-specific like
  `.mvajv-root`) to prevent collisions if embedded.
- Target under 2000 lines total. These are documents, not applications.

## The Anatomy of a Report

Every report follows this skeleton. Not every section is required for every report.
Use what serves the content.

```
TOPBAR
  Brand name (left) · Status/date badge (right, mono, with pulsing dot)
  Scroll progress bar along the top edge

HERO
  Kicker (mono, uppercase, brand accent, with decorative line)
  H1 headline (serif, one word italicized with gradient)
  Deck paragraph (sans, secondary color, max-width 56ch)
  Stat strip (3-7 key metrics in a grid)

SECTIONS (01 through N)
  Section header (mono eyebrow: number and topic, no § and no pill)
  Section H2 (serif, one word italicized in accent color)
  Section body (cards, charts, grids, tables, bars, tiles, splits)

CLOSING ELEMENT
  A call-to-action, a real open question, or the clearest concrete fact
  (serif italic, large, with gradient background on card)

FOOTER
  Brand wordmark (serif) · Version/date (mono, tiny)
```

## Key Patterns (Learn These, Then Improvise)

These are the building blocks. You can combine them, modify them, and invent new
ones. The patterns below capture the visual grammar. When you understand the grammar,
you can write new sentences. `references/components.md` lists more (unit charts, heat
tiles, stacked bars, dot maps, sortable tables, timelines) with tested vanilla code.

### Pattern 1: The Stat Strip

A horizontal grid of 3-7 metrics. Each cell has: an icon (24px, stroked SVG, low
opacity), a large number (display font, color-coded), and a tiny label (mono,
uppercase, tracking wide).

**When to use:** At the top of the page (hero stats), or within a section to
summarize key metrics.

**Design rules:**
- Grid uses `gap: 1px` with the gap color matching the border color, creating
  hairline separators.
- Numbers use `font-variant-numeric: tabular-nums` so they align cleanly.
- On mobile, collapse to 2 columns. On desktop, all items in one row.
- Color-code numbers semantically: accent for primary, green for positive, gold for
  targets, default text color for neutral.

### Pattern 2: The Data Bar

A labeled horizontal bar showing relative magnitude. Used for comparing items in
a category (partner economics, channel performance, budget allocation).

**Structure:**
- Top row: name (with `<small>` subtitle) left, value right.
- Bar track: full-width, muted background. Fill bar: percentage width, colored by
  category. Use `data-color` attributes to style via CSS.
- Footer row: tag/label left, supporting detail right.

**Design rules:**
- Bar track is 6-8px tall. Fill uses the category color at varying opacity.
- Sort by value descending (biggest bar on top) unless there's a reason not to.
- Use `opacity` on bars to signal status: full opacity = confirmed, reduced = pending.
- Bars grow from zero once when they scroll into view (`scaleX`), never on every pass.

### Pattern 3: The Split Grid

Two cards side by side (or stacked on mobile). Used when you have two complementary
data sets: revenue split + governance, before + after, us vs. them.

**Design rules:**
- `grid-template-columns: 1fr 1fr` with `gap: 16px`. Stacks at `max-width: 720px`.
- Each card is a standard card (surface background, 1px border, 16px radius).
- Cards can contain tables, icon-labeled items, or mini stat strips.
- Use contrasting accent colors between the two cards to reinforce the duality.
- When the two cards measure different units, each says which scale it uses.

### Pattern 4: The Timeline / Roadmap

Horizontal or vertical sequence of phases/weeks/milestones.

**Structure:**
- Each phase gets a column (or row on mobile) with: phase label (mono, pill-shaped),
  a list of deliverables, owner tags, and dependency notes.
- Active phase is highlighted with accent border and glow.

**Design rules:**
- Use the same card surface as the rest of the report.
- Phase labels are pills matching section tags (mono, uppercase, tiny).
- Deliverables are in the body font. Owners are bold or tagged.
- A "John's ask" or callout card at the end for special requirements.
- The connecting line draws on scroll and the phase dots pop in sequence.

### Pattern 5: The Closing Question

A full-width card with gradient background (radial gradients from two brand colors,
low opacity, over the surface color). Contains a real open question for the reader or a
call-to-action in large serif italic.

**Design rules:**
- Border uses the primary accent color.
- Label above the question: mono, tiny, uppercase, with a decorative line.
- Question text: display font, italic, 22-36px, max-width 28ch.
- Bold one key phrase in the question (color it with the warning/gold accent).
- Attribution below: mono, tiny, who this question is for.

## Chart.js Integration

When the report includes data visualization:

1. Load Chart.js 4.x from CDN: `https://cdn.jsdelivr.net/npm/chart.js@4.4.1/dist/chart.umd.min.js`
2. Set global defaults to match the report palette:
   ```js
   Chart.defaults.font.family = "'Montserrat', system-ui, sans-serif";
   Chart.defaults.color = '#a8a5b0'; // text-2 equivalent
   ```
3. Use the report's color tokens for datasets. Match border/fill colors to the
   semantic palette.
4. Tooltips: dark background, light text, 1px border matching the line color.
5. Doughnut charts: use `cutout: '68%'` for the modern ring look. Add a center
   label via absolute-positioned div over the canvas.
6. Line charts: `tension: 0.4` for smooth curves, `pointRadius: 0` (show on hover
   only), `fill: true` with low-opacity background for area effect.
7. Grid lines: use the `--line` color. X-axis grid hidden, Y-axis subtle.
8. Prefer hand-built CSS or SVG for bars, unit charts and stacked bars (see
   `references/charts-tables.md`); use Chart.js for lines and rings.

## Brand Adaptation (Configuration, Not Core)

Branding is a color swap, not a design decision. The visual methodology (typography
hierarchy, section structure, stat strips, data bars) stays the same regardless of
brand. This section just tells you how to pick the right accent color.

When creating a report for a specific brand:

1. **Check if a brand skill exists.** Look for loaded skills matching the company:
   `lakeb2b-brand-guidelines`, `span-brand-guidelines`, `ampliz-brand-guidelines`,
   `metricfox-brand-guidelines`, `champions-group-brand`, or any custom brand skill.

2. **Pull the palette.** Extract primary color, accent color, and any secondary
   colors from the brand guidelines. Map them into the custom property system:
   - Brand primary → `--accent`
   - Brand primary light → `--accent-glow`
   - Keep `--positive`, `--warning`, `--negative` as universal semantic colors
     unless the brand has explicit overrides.

3. **Pull typography.** If the brand specifies fonts, use them in place of the
   defaults. Maintain the three-tier system (display/body/mono) even if specific
   faces change.

4. **Footer and topbar.** Use the brand's wordmark style. If the brand has a
   specific tagline or positioning line, include it. Logos follow the brand skill's
   background rules (LakeB2B: white, light grey, purple or navy only, 180px minimum).

5. **When no brand skill exists:** Use the neutral dark palette with purple accent.
   This is the safe default that looks professional for any context.

## CSS Architecture

Every report follows this structure:

```css
.{project}-root {
  /* 1. Custom properties (palette, fonts) */
  /* 2. Base resets */
}

/* Component styles, scoped under .{project}-root */
.{project}-root .{project}-topbar { ... }
.{project}-root .{project}-hero { ... }
/* etc. */
```

**Scoping rules:**
- Every selector starts with `.{project}-root` or is nested under it.
- The project prefix prevents collisions. Use a short, descriptive prefix:
  `mvajv-`, `span-`, `amp-`, `champ-`, `lkb2b-`.
- All CSS custom properties are prefixed: `--mvajv-bg`, `--span-accent`, etc.

**Responsive strategy:**
- Mobile-first. Base styles are for narrow screens.
- `clamp()` for font sizes and spacing (eliminates most breakpoints).
- One or two `@media (min-width: 720px)` breakpoints for grid layout changes.
- Grid tracks that hold wrapping content are `minmax(0, 1fr)`, never bare `1fr`,
  and the element doing the shrinking also carries `min-width: 0`. A bare `1fr`
  resolves to `minmax(auto, 1fr)`, so a long word or a `<pre>` in the content
  pushes the track past the viewport while every child still measures inside it.
- Wide data tables sit in an `overflow-x: auto` wrapper so they scroll in place
  instead of scrolling the page or being clipped by the root.
- `max-width: 1600px` on the shell container, so the report uses the full width on wide screens (Deep dislikes a narrow centered column with dead space either side). Generous horizontal padding
  via `clamp(16px, 4vw, 40px)`.

**Accessibility:**
- `prefers-reduced-motion` media query to disable animations.
- All text meets WCAG AA contrast against its background.
- SVG icons use `stroke` (not fill) for consistent weight, and are decorative
  (no alt text needed, they accompany labels).

2. **Template.** For a new report, propose a template from `references/templates.md` (Campaign Report is the usual fit; Market or Data Snapshot for dataset cuts). If the reader needs one decision page, route to `executive-one-pager`; if it is a client proof page, route to `showcase-page`.
3. **Components from 21st.dev.** If the 21st.dev MCP is connected (`search`, `get_inspiration`, `get_component`), search the 3 to 5 key components with the queries in `references/components.md`, pick, and pull code for at most two (free tier: 2 a day). Port to this skill's scoped vanilla CSS and credit the id in a comment. Not connected: say so in one line and use the patterns above plus the kit fallbacks. Never write an API key into a file.
4. **Micro-interactions from MicroKit.** Every interactive element gets a hover, focus and touch response from `references/micro-interactions.md`: row accent bars on tables, animated row reorder on sortable tables, label swap and arrow slide-through on buttons, top-rail glow on chips. One per element, 200 to 500ms, brand colours.
5. **Charts and motion.** Pick charts by data shape and keep separate scales for different units (`references/charts-tables.md`). Animate bars, dots and lines to their values once on scroll, keep final values in the HTML, honour `prefers-reduced-motion`, and support `?static=1` for PDF and PNG exports (`references/motion.md`).

## Process: How to Build a Report

0. **This skill is loaded before any page is built, not after it is judged.** Deep reads
   every HTML deliverable as a designed page and rejects a wall of prose: "way too much text
   without anything to break up the monotony." The gate is not the finished file being
   attractive, it is this skill being the source of the build: card and grid components,
   a visual in every section, type hierarchy doing the work. A source document that renders
   as table after table with no break is a defect whatever its content, so the first design
   act is choosing which of these patterns breaks each run of prose: stat strip, split grid,
   flow steps, big-number band, quote, a card grid. Paragraphs are the exception in a section,
   never its body.

1. **Understand the content.** What data, decisions, metrics, and narrative does
   this report convey? What's the single most important takeaway?

2. **Identify the brand.** Which company is this for? Load the brand skill if one
   exists. Set up the palette.

3. **Choose a project prefix.** Short, unique, descriptive. This becomes the CSS
   namespace.

3b. **Write the design direction before the first CSS rule**, as a comment at the top of
   the stylesheet: which grounds alternate and in what order, the one dark ground, where each
   brand colour is allowed (accent, mark, rule) and where it is not (bands, gradient fills),
   the three type roles, one section rhythm (number, pill, headline, lede at the same offset in
   every section), explicit light text on dark. Then write every rule against that comment.
   A page assembled section by section without it makes a different visual decision in each
   section and reads as off-brand even when every hex is correct. Client pages get their own
   stylesheet: never inherit CSS from an internal report page. Worked example, read it when
   building a tiered proposal: `Celsus/Efforts/Active/Ryan Pilot Proposal/build/build_proposal.py`
   (DESIGN DIRECTION comment, section 02 interactive dossier and decision graph) and its
   `verify_v5.py` (per-element contrast measured from rendered pixels, interaction assertions,
   overflow, console, section shots in one run).

4. **Outline the sections.** What are the 4-8 chapters of this story? What pattern
   (stat strip, data bars, split grid, timeline, table) best serves each section?

5. **Write the hero first.** The headline, deck, and stat strip set the tone for
   everything. If the hero is wrong, the report is wrong.

6. **Build section by section.** Each section: header, h2 thesis, visual body.
   No section should be just a wall of text.

7. **Add charts if data warrants it.** Doughnut for composition, line for trends,
   bar for comparison. Keep it to 1-2 Chart.js charts max. Reports are documents, not
   dashboards.

8. **Write the closing.** A call-to-action, a real open question for the reader,
   or the clearest concrete fact on the page. Never an aphorism or kicker line
   (the `no-ai-slop` gate deletes those).

9. **Test contrast.** On dark backgrounds, verify all text is explicitly light.
   On colored backgrounds, verify readability. Never rely on inherited color.

10. **Verify the 3-10-30 rule.** Mentally simulate a busy reader:
    - Can they get the headline numbers without scrolling? (3s)
    - Can they see all section topics from the headers alone? (10s)
    - Is every data point in a visual pattern, not buried in text? (30s)

11. **Keep it under 2000 lines.** If you're exceeding that, the report is trying
    to do too much. Split into multiple reports or simplify.

## Presenting it live: pair the page with a readout script

When the page will be shown to a team, deliver two files: the HTML and a
markdown readout script.

- The script names the exact file path, tells the audience to open it, then
  walks the sections in the page's own order with a cue for each ("Press <section>")
  so speaker and screen never drift.
- **The screen carries only what the audience must answer.** Questions the team
  should respond to live go on the page as a numbered list with owner tags.
  Questions that are really asks of one named person belong in the readout script
  or chat, never on the screen: a page full of your own to-dos sends the meeting
  off track.
- **Label each figure's check status separately**, one line in the hero and again
  in the footer: what you verified against the live source and when, what is quoted
  as reported and not re-measured, what sits behind credentials and was not
  queried. A single blanket "figures unverified" disclaimer is wrong the moment
  you have checked part of them, and it goes stale when a source becomes
  checkable: update the line in the same edit that gains the check.

When Deep will present the page rather than send it, also write the **spoken** script:

- Time it to the page's own section order and title each block with the section it
  belongs to, so he can pick up mid-page when a meeting runs short.
- Bracket every aside that is not said aloud: pauses, looks to a named person, reads
  of an open question. Speaker and screen stay aligned only if the off-script bits
  are visually distinct from the lines.
- One line per card or row. The page carries the detail; the script says what to
  emphasise and stops.
- End with a read-back of what was decided and what is still open, then the next
  step with an owner, so the meeting closes on commitments rather than content.
- Keep internal-only rules (never quote a floor, a ceiling, a per-record price)
  in the script as reminders. They are spoken guidance for the presenter, not
  text that may ever reach the screen.

## Hard Rules

1. **Never use em dashes or en dashes**, including headings, labels, chart text, date ranges and PDF exports. Periods, commas, colons, or restructure.
1b. **Never use the section sign (§)** or a pill-outlined section tag. Section eyebrows are a bare mono number and topic.
2. **Always check contrast.** Text on dark or colored backgrounds must be
   explicitly set to a light color. Never rely on inheritance.
3. **Scope all CSS.** Every selector under the project root class.
4. **One file.** All HTML, CSS, and JS in a single `.html` file.
5. **No frameworks.** Vanilla HTML, CSS, JS. Google Fonts + Chart.js CDN only. Components pulled from 21st.dev are ported to vanilla.
6. **Numbers first.** If a section has key metrics, they go at the top of the
   section, not buried in prose.
7. **Mobile-first responsive.** Base styles for narrow, `clamp()` for scaling,
   media queries for layout shifts only.
8. **Never invent a number.** Every figure comes from the source; rates and shares
   computed from stated figures are allowed and labeled as computed.

## Verify before delivery (mandatory)

This output is visual, so reading the source does not tell you whether it worked. Render it and look at it.

```bash
python3 visual-verify/scripts/audit.py <output.html> --width 390
python3 visual-verify/scripts/audit.py <output.html> --width 1440
python3 visual-verify/scripts/shoot.py <output.html> --widths 390,1440 --themes light
```

Then **open every screenshot with the Read tool** and critique it. Not the file listing, the images. A screenshot you did not look at has verified nothing.

The four things this catches that nothing else does:

1. **Contrast measured against the composited background**, including transparency stacking, rather than against the hex you intended.
2. **Horizontal overflow at 390px**, with the offending element named.
3. **Content that overflows its container** once real text length replaced the sample.
4. **Flat hierarchy:** three elements competing where one should dominate. Only the eye finds this.

Add three checks of your own:

5. **The Paddle bar.** Would Paddle ship this? Numbers on hairlines with mono labels, a real visual in every section, hover and focus responses on every interactive element.
6. **Copy gate.** `no-ai-slop` in Gate mode on every line; zero dashes in the HTML and any PDF (`pdftotext file.pdf -` then grep for the two dash characters).
7. **Width.** At 1440 the report spans the page with a gutter, not a narrow column.

And when the page has controls that keep state (filters, checkboxes, scorecards), drive them in Playwright and assert what each click actually did: the filtered row count, a verdict string after the last required item is set, the state surviving a reload, and reset clearing it. A page that audits clean can still have dead buttons.

Assert on `getComputedStyle(el).textTransform` before comparing label text. CSS `text-transform: uppercase` normalises `textContent`, so a case-sensitive assert on a mono label fails against the very string the page renders. Read the computed text, not the source string.

The showcase on a proposal page is a working component, not a picture of one: hover reveals, click pins, a toggle changes state and copy, nodes take keyboard focus. If the page needs to "show what the client gets", build it with state from the start; a static mockup gets rejected as mediocre and is rebuilt anyway.

A vision-model pass on a screenshot grades legibility and overlap, not brand fit or taste. It will call an off-brand page excellent. Use it for overlap and cut-off text only; judge hierarchy, colour discipline and rhythm yourself against the design direction comment and the brand skill.

Zero FAILs before delivery. Every WARN either fixed or justified in one line. If no browser is available, say so and label the output **unverified**, listing what was not checked.

## Mechanism figure: the Anatomy skill (verified 2026-10-26)

When a page must explain HOW something works and the idea has a physical mechanism (rate limiter, cache, pipeline, deploy flow, verification gate), an `anatomy` isometric figure can replace a whole paragraph: a real object built from shaded parts, SVG output, optional WebGL, one HTML file the reader can poke.

- Installed at `~/.hermes/skills/creative/anatomy` (wheresryan22/anatomy, MIT, 0 npm deps, Node 20.10+). Verified here: its 290 tests pass and `examples/push-button/build.mjs` builds and renders a complete framed figure with a live readout.
- It is NOT a chart library: no axes, no series, no data plots. Numbers only appear as a live readout inside the figure. Charts stay with this skill's chart set.
- It is slow to build on purpose (parts list, geometry, audit of every joint). Budget one long session; use it only when the figure earns its place over a flat diagram.
- Capture scripts need Chrome. Build with `node <example>/build.mjs` (`--light` for a light card).
- Trigger words from the user: isometric, exploded view, cutaway, "how it works" as a figure. Otherwise keep the existing flat style.
