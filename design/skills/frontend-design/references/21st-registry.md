# 21st.dev component registry

Deep's standing rule: **21st.dev components are non-negotiable for all front-end work.** Check the registry before hand-writing any standard component (filter bar, command palette, data table, date picker, toast, stepper, chart wrapper). Writing it custom when 21st has it is the failure; say so explicitly if you fall back.

## Setup (once per machine)

The registry needs an API key as `TWENTY_FIRST_API_KEY` in `~/.hermes/.env`. The key value is Deep's to paste (never write a pasted secret yourself, see `credential-and-secret-handling`): add the variable line empty and hand him the file. Verify with a request that only checks status, never echo the key:

Use the current authenticated MCP endpoint `https://21st.dev/api/mcp` with `x-api-key` or Bearer from `TWENTY_FIRST_API_KEY`. Call JSON-RPC `tools/list`, then use the returned schemas for `search` and `get_component`. Send `Accept: application/json, text/event-stream`; responses may be SSE `data:` JSON. Discovery: `https://21st.dev/mcp.md` and `https://21st.dev/auth.md`. The old `registry.21st.dev/api/registry/search` route can return 404; that does not mean the stored key is missing. A successful tools/search result is the auth proof. Never print the key.

If no named 21st tool appears in the session catalog, the authenticated HTTPS MCP endpoint remains usable without modifying Hermes configuration. Check existing access before asking Deep to reconnect or supply a key.

## Install

Install from the component's page on 21st.dev: it shows the exact `npx shadcn@latest add https://registry.21st.dev/r/<owner>/<name> --yes --overwrite` command. Run it from the project root with the key exported in that shell. For authenticated registry installation, use a `components.json` registry with `url: "https://21st.dev/r/{name}"` and `params: {"api_key": "${TWENTY_FIRST_API_KEY}"}`. The registry may reject the header-only authentication accepted by MCP. Keep the placeholder in config, never the value, and redact expanded-key CLI errors before printing them. Add Kokonut as `"@kokonutui": "https://kokonutui.com/r/{name}.json"`, then `npx shadcn@latest add @kokonutui/<name> --yes`. Inspect the CLI's actual output path; explicit registry targets can land under `src/components` despite root-level aliases. Preserve author/license notices and record source URLs plus adaptations.

Then follow the standard shadcn hygiene from `span-agent-development/references/ui-stack.md`: rewrite any `from "cn"` imports to `@/lib/utils`, typecheck. Typecheck is the only proof a component actually landed; a failed CLI that you "proceed without" produces imports for files that do not exist.

## Quirks

- **Not every entry installs.** Some components answer `[User not found]` from the registry even with a valid key, and the JSON dump from `npx @21st/registry@latest search` may show entries with no install command. If `npx shadcn add` fails twice on one entry, stop: fall back to the shadcn/ui primitive that covers the behaviour (for a search UI, shadcn `command.tsx`/cmdk plus a controlled filter state) and note the substitution in the report. Do not keep retrying the same URL.
- **Registry content is demo code.** 21st components ship with their own styling and hard-coded example data. Expect to retheme them onto the project's CSS variables and replace the sample data with real props; that adaptation is part of the install, not a reason to skip it.
- **Check the dependency surface before importing.** Some entries pull framer-motion or other heavy deps the project does not carry. If the install would add a dependency the stack deliberately avoids, prefer the primitive fallback over growing the bundle for a component.
- **A CSS-driven component often ships its rules as keyframes only.** The registry payload and the component file can carry the animation keyframes and zero class rules, so the component installs, typechecks, and renders as a static element. Find the real stylesheet before concluding the component is broken: pull the component's compiled demo bundle off the published CDN (`cdn.21st.dev`), strip its inline `<style>` (or grep the bundle for the component's class prefix), and copy the rules into the project as a scoped stylesheet. Extracted demo CSS targets its demo markup, so re-scope the selectors to your wrapper class and delete rules for elements the component does not render.
- **Never edit the installed component file as your customization home.** The next `shadcn add` for that entry (a version bump, a teammate, a retry) rewrites the file from the registry and silently reverts your adaptation. Put project-specific behaviour in the consuming component and styling in the project stylesheet under a wrapper class you own, and re-apply anything that must live inside the component from a tracked note. Verify with `git status` before trusting that a customization is durable.
- **Prove the page under test is your page.** Ports get shared: a dev server can hold loopback (`127.0.0.1`) while your app server holds the wildcard interface, and `localhost:<port>` then serves someone else's app that passes every visual check with the wrong content. Before any render-level verification, `lsof -nP -iTCP:<port> -sTCP:LISTEN` to list every owner, then confirm the address you are about to drive returns your build: `curl -s http://<host>:<port>/ | grep -c <a string only your bundle contains>`, and prefer the LAN IP (`ipconfig getifaddr en0`) when loopback is contested.
