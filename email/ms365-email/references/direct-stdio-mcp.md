# Direct stdio calls to a configured MCP server

Use when a tool exists on a configured stdio MCP server (per `config.yaml`) but is not exposed in the live Hermes toolset. Spawning the configured server and speaking JSON-RPC over stdio reaches the same tool with the same auth.

1. **Read the server block.** `~/.hermes/config.yaml` (or `$HERMES_HOME/config.yaml`) under `mcp_servers.<name>`: `command`, `args`, `env`, and any `--enabled-tools` regex in args. Extend a copy of the regex if it excludes the tool you need, and pass the config `env` into the child environment. The sandbox has no `yaml` module, so regex the block: cut it at the next two-space-indented key (`\n {2}[a-z_]+:`), never at `\n\S`, because sibling servers under `mcp_servers:` are indented two spaces, so an `\n\S` cut never fires and your args pattern silently swallows the next server's argv (a stray script path lands in the child's command line). Print the raw block before spawning so a parse slip is visible in the same output.
2. **Spawn.** `subprocess.Popen(command + args, stdin=PIPE, stdout=PIPE, stderr=DEVNULL, text=True)`.
3. **Handshake, one JSON object per line, flush after each write:**
   - initialize: `{"jsonrpc":"2.0","id":1,"method":"initialize","params":{"protocolVersion":"2024-11-05","capabilities":{},"clientInfo":{"name":"...","version":"1.0"}}}` (known-good protocol version)
   - then the notification: `{"jsonrpc":"2.0","method":"notifications/initialized"}` (no `id`)
   - then `tools/list` (its own id) and take the exact tool name from the result: server-side spelling can differ from the connector's exposed name, and the reply doubles as the server-ready check before you spend the real call.
   - then the call: `{"jsonrpc":"2.0","id":3,"method":"tools/call","params":{"name":"<tool-name>","arguments":{...}}}`
4. **Read responses by `id`.** Read stdout line by line, keep only the object whose `id` matches the request, skip parseable-but-unrelated lines. Fail on a response carrying `error`, on EOF or process exit, or on a deadline (90s suits Graph-backed calls). The tool payload arrives as `result.content[].text` (often JSON encoded as text); check `result.isError` too.
5. **Clean up in `finally`.** Terminate the process; kill if terminate times out.
6. **Still verify through the normal connector read tools.** Transport-level success is not state success.

**Before parking a mail task on an inbox card, prove that lane can spawn at all:** run `hermes kanban dispatch --dry-run --json` and check the card is not listed in `skipped_nonspawnable`. The usual cause is the quota guard (`~/.hermes/scripts/kanban_quota_guard.py`, cron every 15 min), which rewrites `kanban.dispatch_profiles` from live provider headroom and drops it to `['default']` (or `[]`, a full pause) while a provider sits inside its reserve. While that holds, every inbox card stays in `ready` with no worker, and the draft Deep is waiting for never exists. Stage it from the main lane over stdio instead, then close the inbox card as done by hand.

The default profile's ms365 block is calendar-read only (scopes `User.Read Calendars.Read`). Take the mail-capable block from `~/.hermes/profiles/inbox/config.yaml` (read only, never edit it): its `--enabled-tools` regex and `User.Read Mail.Read Mail.ReadWrite Calendars.Read` scopes, with `MS365_MCP_TENANT_ID` in env. Verified: `list-mail-folder-messages`, `create-draft-email` and `get-mail-message` work from the main lane this way, so never say the main lane has no mail access and do not park a draft on an inbox card before trying it. Tool names use hyphens over stdio.

The `--enabled-tools` regex in the server's config already covers the common mail tools; when spawning standalone, reuse the config's args rather than inventing a fresh set, so scope and auth match the configured server.

In an unattended kanban run `execute_code` is blocked, so use `terminal` with a script file run by `/Users/deep/.hermes/hermes-agent/venv/bin/python` (system python3 has no `mcp` package): `sys.path.insert(0, '/Users/deep/.hermes/profiles/inbox/inbox-bot'); import inbox_bot as B; m = B.McpMail(); await m.open()` then `m.call(tool, 'deep@lakeb2b.com', ...)`. `m.create_reply_draft(acct, messageId, text, reply_all=False)` makes the reply, patches clean html with the quoted thread and reads back; a separate `update-mail-message` with `body={'subject': ...}` fixes the subject. Verified for a legal reply draft on 12 Nov. The helper has no send tool.

Calendar reads work the same way from the main lane: the default profile's block is calendar-read only, so spawn it (config args as-is, narrow `--enabled-tools` to `^(get-calendar-view|list-calendar-events|get-calendar-event)$` when you only want the view) and call `get-calendar-view` with an ISO start/end range, `select` trimmed to `subject,start,end,attendees`, and a `top` cap. Read `value[].start.dateTime` as-is and convert to IST before quoting an hour to Deep: Graph returns a UTC clock value with a `+00:00`-style suffix, so an event he calls 5:00 PM reads as 11:30 in the payload, and a runbook that quotes the raw number schedules the meeting at the wrong hour.
