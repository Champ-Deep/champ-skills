# ms365 Email (Outlook connector)

Provider commands for Deep's Outlook mailbox through the configured `ms365` MCP server (`mcp__ms365__*` tools): compose, attach, and read-back verification. `email-inbox-triage` owns thread policy and prioritization; `himalaya` owns terminal IMAP/SMTP.

## When to Use

- New outbound mail must exist as an unsent Outlook draft, optionally with a document attached.
- Verify a draft's recipients, subject, attachments, or draft state before Deep sends it.
- Attach a file to an existing draft when only the message id is known.
- Deep has explicitly approved sending this exact mail, and the send must be executed and proven by read-back.
- Reading an attachment someone else sent for analysis (an export Deep was forwarded, a report the sender owns): same pair as step 6, `list_mail_attachments` with `select` trimmed to `id,name,size` so inline images never come back, then `download_bytes_to_file` with `target /me/messages/{messageId}/attachments/{attachmentId}/$value` to a scratch path that does not exist yet. The downloaded file is an input to analysis, so note its size and the sender's stated cutoff alongside the figures drawn from it.
- Bulk read-only audit of the whole Drafts folder (formatting residue, spam triggers, unfilled `[CONFIRM]` tags, missing recipients) plus send-readiness triage of every draft into needs-confirm / empty-to / stale / ready, before a cleanup or redraft pass: `references/bulk-draft-audit.md`, driven by `scripts/draft_audit.py`.

Don't use for: inbox triage or reply policy (`email-inbox-triage`), terminal IMAP/SMTP (`himalaya`), Gmail or Drive (`google-workspace`).

## Always-on rules

- Always stage as a draft, never send, whatever the request says. Deep's instruction "send this to X" means create the draft addressed to X; he presses Send. Learned the hard way on 2026-11-04 when a "send" was executed through Outlook AppleScript and he corrected it: the goal is always to draft. Return the draft's `webLink`, never the raw message id, so he can open it in one click.
- Deliver attachments inside the draft. If Deep asks for "the doc", the file is attached to the Outlook draft, not merely linked in chat.
- Every write is verified by read-back before it is reported done. A successful tool call is not a successful draft.
- Never put a link in the body that was not actually produced. Omit the sentence and say the link is unavailable rather than inserting a placeholder.
- Never write a body claim in the past tense about a side effect you have not executed and read back ("I have added you to the repo", "the key is on your machine"): the draft is sent later without you, so an unperformed action ships to the recipient as a fact. Do the action first (invite, share, upload), verify it, then stage; if it cannot happen yet, write it as a commitment ("I will add you once you accept") or drop the sentence and put the action on the decision card. The same applies to the attachment sentence: never write "attached", "see the file", or a list of named files until `list_mail_attachments` shows every one of them. The body cannot be edited after the draft exists, so a body promising three attachments with one failed attach ships that false claim with the mail.
- On a folder-wide audit or cleanup, confirmations come before rewrites: surface every `[CONFIRM]` gap and get Deep's answers first, then touch any draft. There is no partial edit, so a draft rewritten while a question is still open has to be patched again the moment the answer lands (a body edit is a whole-body patch with a required read-back, step 3), and the stale copy competes with the fixed one in the same folder.
- A cleanup pass must not multiply drafts. Deep's standing limit is explicit: never hand back "another 100 drafts". Probe for an in-place update path before planning any rewrite (step 9, and the bulk-audit reference); where none is verified, rewrite only the drafts that are actually going out, leave the rest untouched, and name SEND/DELETE pairs instead of cloning the folder.
- **A redraft of an existing thread is a reply, never a fresh mail.** When Deep deletes his drafts and asks for them again, or a cleanup pass replaces drafts on live threads, each replacement is staged through the reply path against the original inbound message id so the prior conversation is quoted underneath. A standalone draft carrying the same text is the wrong artifact even when every sentence matches: he opens it expecting the thread, and to the recipient a mail with no quoted history reads as a cold new approach to someone already answered. His standing correction, so it holds for every replacement.

## Procedure

0. **Search Drafts and Sent for the same ask before creating anything.** An unsent draft already sitting there has no partial edit: cc, subject and body are whole-value patches that each need a read-back (step 3), and two plausible drafts in one folder is how Deep sends the wrong one: fix it in place when a patch covers the change, otherwise replace it and name both subjects in the same reply (SEND the replacement, DELETE the stale one). When the earlier mail already went out, branch into a fresh follow-up instead of restating it. A failed create with an unknown outcome is this same search, before any retry.
1. **Ground the draft in the live thread.** Before writing, find what the team already said: one `mcp__ms365__list_mail_messages` call with a KQL `search` OR-ing `to:`/`from:` addresses and a `received>=` floor, `select` limited to id/subject/from/receivedDateTime/bodyPreview/isRead, `top: 25`, then page with `@odata.nextLink`. Read full bodies only for the threads in scope via `get_mail_message`. Re-drafting an unanswered thread without its last reply loses the promised date and the ticket number. **A mailbox search only proves what arrived:** when the question is whether an outgoing message exists at all, also search `list_mail_folder_messages` on `drafts` and `sentitems`, because unsent work lives in Drafts and `$search` over received mail never sees it. Full recipe: `references/thread-search-recipes.md`.
2. **Resolve scope.** Recipient address(es) and display names, subject, body facts, attachment file path. Confirm the attachment exists, is non-empty, and note its size and MIME type before creating anything. Settle every fact before this point: person names checked against a source (vault, thread, the document itself) rather than retyped from meeting notes, amounts read out of the source PDF or invoice line by line, and the full attachment list final. A draft's body is edited only by patching the whole body (`update-mail-message`, step 3) and proving the new text on a read-back, so a fact fixed later means that patch, and a patch that does not stick means a replacement draft plus a stale duplicate Deep must delete by hand. **What the draft says is not this skill's call:** voice, structure and body formatting come from `deep-email-voice`, which also owns the recipient-resolution lookup order. Follow it before step 4.
3. **Create the draft.** `mcp__ms365__create_draft_email` with explicit `toRecipients`/`ccRecipients`/`bccRecipients`, `subject`, and `body: {contentType: "text", content: ...}` unless `deep-email-voice` specifies html. For a reply draft, `create_reply_draft`/`create_reply_all_draft` take a `Comment` and set the contentType themselves, which is why replies need the html treatment below. Set every recipient field explicitly rather than relying on defaults. Keep the returned `id` and `webLink`.
   - **A reply draft (`create_reply_draft` / `create_reply_all_draft`) arrives as one run-on block, and html cannot be passed at creation.** Graph stores the `Comment` as one string, so every `\n` you send disappears on read-back and the quoted history lands underneath unstyled; the create tool takes only the comment text. Fix it by patching the draft's body (the path the inbox bot uses, `inbox-bot` skill): read the draft back, run the reply text plus that quoted body through `build_clean_reply_html` in `inbox_bot.py`, call `update-mail-message` with the message body `{'contentType': 'html', 'content': formatted}`, then read back again and assert the reply text is present. Only when the patch does not stick do you create a replacement and tell Deep which draft to DELETE.
   - Recipients on a reply draft come from the quoted thread, not from arguments you pass. Read the returned `toRecipients`/`ccRecipients` before reporting the draft: a reply-all to the wrong thread is otherwise invisible until Deep opens it.
   - **On a reply draft, `ccRecipients`, `subject` and the message body are each patchable after creation with `update-mail-message`.** A missing cc, an en dash left in the subject, or a run-on body is one patch plus a read-back, not a second draft and a SEND/DELETE pair. A body patch replaces the entire body, so carry the quoted history forward from the read-back draft (the reply formatter does this) and assert both the reply text and the quoted history on the next read-back. Creation success also proves the call, not the thread linkage: read the draft back and confirm the quoted history is in the body. Full recipe: `references/bulk-draft-audit.md` section 5.
4. **Attach the file.** Build `body` as `@odata.type: #microsoft.graph.fileAttachment`, `name`, `contentType`, `isInline: false`, `contentBytes` as base64 of the raw bytes, with `messageId` as the top-level argument.
   - **Base64 larger than ~2-3 KB goes through the stdio recipe in `references/direct-stdio-mcp.md`, never an inline tool call.** Past that size an inline argument can break the tool call's own JSON envelope (rejected as invalid JSON before it executes), so inline is not a fallback worth trying: go straight to stdio. Even when it does parse, emitting the blob as a tool-call argument means generating the whole base64 through my own output tokens: a 20 KB zip costs ~27 KB of typed text and a single transcription error corrupts the attachment with no error surfacing. Generate the base64 inside `execute_code`/stdio code. This applies whether or not the tool is exposed in the live toolset; use stdio whenever the payload is big, not only when the tool is missing. Handing the attach to a subagent does not move the cost: the child reads the same bytes into its own context and re-emits them in its own tool call, and it becomes a second writer on a draft that has no edit path. Generate the base64 once, in the stdio session.
   - **A file too big to inline goes through Graph's upload session, and that route never carries the bytes through a tool call at all.** If Graph rejects `contentBytes`, or the file is already known to be several MB, call `create_mail_attachment_upload_session`: its arguments are only `messageId` plus an `AttachmentItem` of `{attachmentType: "file", name, size, contentType}`, so tiny arguments go through the live connector even where `contentBytes` would not. Then PUT the raw bytes at the returned `uploadUrl` with plain HTTP: chunks of a few MB, each with `Content-Range: bytes <start>-<end>/<total>` and no Authorization header (Graph signs the URL itself), `200` on intermediate chunks and `201` on the last. Verified end to end on a 5.6 MB PDF in two chunks. Prefer it to packing several MB of base64 into one stdio JSON line: the bytes stay out of the message envelope entirely, and a failed chunk is retried without recreating the draft. Close with the same read-back as any other attach, `list_mail_attachments` showing the exact filename.
5. **Verify.** To read back an html body as html (table cells, `<p>` breaks), spawn the server with env `MS365_MCP_BODY_FORMAT=html`: by default the softeria server sends `Prefer: outlook.body-content-type="text"` on every GET, so `get-mail-message` always reports `contentType: text` with a flattened render and cannot prove the html patch stuck. `get_mail_message` (expect `isDraft: true`, `hasAttachments: true`, correct recipients and subject) and `list_mail_attachments` (exact filename, size, contentType). Report only what the read-back shows. For several drafts created in one turn, read every one back: the create response for draft A does not prove draft B exists or that its To field is right. For a multi-paragraph body, also check the read-back body itself for paragraph breaks: a reply drafted as plain text reads back as one block, and that is the signal to patch the body as html (step 3) rather than to hand Deep a draft he has to reformat.
6. **Replace a stale attachment.** If the local file changed after it was attached, the draft still serves the old bytes. Re-run `add_mail_attachment` with the new content, then `delete_mail_attachment` the old attachment id (`confirm: true`), then `list_mail_attachments` again and confirm the list contains exactly the intended set: new file present, old id gone, expected count.
7. **Deep asks "confirm it has the changes".** Filename and size are not proof of content. Download the attached bytes with `mcp__ms365__download_bytes_to_file` (target `/me/messages/{messageId}/attachments/{attachmentId}/$value`, write to a scratch path that does not exist yet) and byte-compare against the canonical local file before answering. For a small text or HTML attachment there is a shorter path: `list_mail_attachments` already returns `contentBytes`, so decode it in code and sha256-compare against the local file, no download round-trip. Graph's reported `size` can exceed the real decoded byte count, so neither a size match nor a size mismatch proves anything; the hash is the proof.
8. **Hand back.** Reply with the clickable `webLink`, recipient, subject, attachment filename, and any body content still awaiting Deep's decision. The draft stays unsent until step 9.
9. **Send, only on explicit approval.** The tool description's promise of a send path is not evidence: confirm a send-capable or draft-update-capable tool actually exists in the live toolset before building a plan around one, and say plainly which mechanism you found or didn't. The same probe governs a cleanup pass: absent an update tool, the pass stages replacements and names SEND/DELETE pairs instead of promising in-place fixes. When Deep has approved sending this exact mail:
   - **Resolve the send mechanism at scope time (step 1), not at the end.** Probe in order: (a) `tools/list` on the ms365 server for a send-capable tool, (b) Outlook for Mac via AppleScript, (c) `himalaya account list` for a configured SMTP account. Raise any missing permission, or the fallback of Deep pressing Send on the staged draft, as a decision card while the draft is being staged, so a grant never becomes the last blocker right before a deadline.
   - **Probe macOS automation consent with a real object query, never `get version`.** `tell application "Microsoft Outlook" to get version` answers even when automation consent is missing, so it proves nothing about the send path; query an object instead (`count messages of folder "Drafts"`). Error `-1743 Not authorized to send Apple events` means the TCC automation grant is absent: Deep enables it at System Settings → Privacy & Security → Automation → (host app) → Microsoft Outlook, or sends the staged draft himself.
   - **Outlook for Mac (new Outlook) cannot save an AppleScript draft.** `save m` on an outgoing message fails with -1701 and the message is discarded; `every outgoing message` enumerates nothing. For drafts with attachments use Graph: `create_draft_email`, then `add-mail-attachment` over the stdio recipe (a 0.9 MB file attached in one call; keep single-file HTML under 3 MB by downscaling embedded images to JPEG). AppleScript is only good for `send`, which Deep forbids.
   - **Send, then prove it.** After the send call returns, read back: `get_mail_message` shows `isDraft: false` with `sentDateTime` set, or the subject appears in Sent Items. The send call's own success is not proof; a mail that silently stays in Drafts looks exactly like success from the caller's side.
   - If no mechanism is available, say so plainly, leave the draft staged with its `webLink`, and name the decision card. Never claim sent.
10. **Batch staging for a handoff pack.** Several drafts with attachments can go out in ONE stdio session: loop the `create-draft-email` calls over one spawned server, each carrying its own `attachments` array, and read each response by its own id. That beats a spawn per draft, and unlike the live connector the stdio call takes attachments inline, so no follow-up attach step is needed. Then read every draft back through the live `get_mail_message`/`list_mail_attachments` pair: the create response for draft A does not prove draft B exists or that its To field is right.

   When a task batch needs many mails staged: resolve every recipient first by searching the vault (regex a person-name fragment against `[a-z0-9._-]+@domain` across `Atlas/`, `_config/`, `Calendar/`, `Efforts/`); then create the drafts, several `create_draft_email` calls per turn is fine. Deliver them as a per-day pack at `Atlas/Ops/Dispatch/Ready to Send <date>.md` with four sections: **GO** (table: subject | To | Kanban card id), paste-ready WhatsApp/Flock texts, **WAIT** (drafts held and why), and work running without Deep. Each GO row ties to a card whose body names the exact draft subject, so one reply (`sent`) closes both surfaces. The card is created blocked with the `kanban-task-intake` decision shape and lists every staged subject with its To and cc, because Deep answers from the card and never opens the Drafts folder to discover what he is approving; state the default (`hold`) and its deadline so silence is an answer. Address discovery, batch drafting and card pairing are coordinated with `kanban-task-intake`.

## Pitfalls

- **`list_mail_attachments` on a marketing or delivery mail can return megabytes of inline base64.** Every `isInline: true` image rides along as `contentBytes`, so the tool result spills to a cache file instead of the conversation, and that spilled JSON carries raw control characters a strict `json.loads` rejects. Parse it with the tolerant `json_parse` helper from `hermes_tools`, not `json.loads`. When you only need the file inventory, ask for `name,contentType,size,id` so `contentBytes` never comes back.
- Attaching before checking the file: the draft exists but the deliverable cannot complete, leaving a half-built draft. Validate path, size, and type first.
- Asking for missing data in prose when you could attach the input sheet. Prefill every field you already know and set dropdowns on the choice fields, so the recipient fills gaps instead of re-typing what the mail already carried; verify the written sheet by reopening it and asserting row counts, not by trusting the writer call.
- Base64 mistakes: `contentBytes` is base64 of the raw bytes, not a path or hex. Python: `base64.b64encode(Path(p).read_bytes()).decode()`.
- Typing `contentBytes` by hand into a tool-call argument: it multiplies output tokens by ~1.33 and a single transcription error silently corrupts the attachment. Generate the base64 in code and pass it over stdio.
- Reporting "the attachment is too fragile to add, attach it yourself" without having tried: the attachment is required, so an unattempted claim dumps the step on Deep. Attach in code first (step 4 with the stdio recipe); only a real error from Graph, quoted verbatim, downgrades the handoff to "attach before sending", and the draft then reads `hasAttachments: false` on read-back.
- Claiming success from the attach call's `success: true` alone. The only proof is `list_mail_attachments` showing the file.
- Leaving the superseded attachment in place after re-attaching an edited file: Deep sends two versions of the doc. Delete the old attachment id and re-list; the final count must match the intended set exactly.
- Stripping internal markings or reviewer notes from a file with no pre-edit snapshot: when Deep later asks "exactly what changed", you can only answer from memory. Copy the pre-cleanup file to scratch first, then diff old vs new and report the exact deltas.
- Returning the OData `id` instead of `webLink`: Deep cannot open the draft from the id.
- Parsing the `mcp_servers` block out of `config.yaml` inside `execute_code`: the sandbox has no `yaml` module. Read the block with `search_files`/`read_file` or parse it in `terminal`, which has the project interpreter.
- Sending a config-reading command through `terminal` that shells out to a language one-liner (`python3 - <<'EOF'`) instead of using the native tools: the gateway's command guard blocks shell text that looks like it would restart or stop the gateway, and the guard matches words, not intent, so the whole command dies before a byte of your parser runs. Read the block with `search_files`/`read_file` and build the child argv in `execute_code`, which never goes through that guard.
- A `create_draft_email` that fails with a transport error (fetch failed, timeout) has an unknown outcome: search `list_mail_folder_messages` on `drafts` for the subject and recipient before re-issuing, because a blind retry leaves two identical drafts and nothing merges them back into one.
- Draft body naming a shareable page or document link that was never actually published.
- Stating an assumption as a fact. If the draft needs a detail nobody confirmed (who approves an access request, which domain TLD to buy), write the conditional sentence with the tag `[CONFIRM: field]` so the gap is greppable, then list every such assumption in the reply so he can strike it before sending. A draft still carrying tags is not sendable as-is, so name it and its tags on the decision card rather than reporting the draft as ready.
- Guessing a recipient's address because the person is obviously real: a wrong address turns a review step into a sent misfire. Search the vault; if no address exists in the vault or the mailbox, leave `toRecipients` empty, put the draft under WAIT in the pack, and flag the missing address in your reply. Empty To is recoverable, a wrong To is not.
- Reporting old vault rows as open work without saying their state is unverified. Mail threads and task rows drift apart: label each bucket (live now, unconfirmed) and name the sources checked and not checked.
- Treating a successful `get version`, or an AppleScript that returned without an error, as proof the send path works: version answers without macOS automation consent, and the script only proves it ran, not that the message left the Drafts folder. Probe with an object query before promising the send, and read the message state back after it.
- Fixing a wrong name, amount, or missing attachment AFTER the draft exists. cc and the body take an `update-mail-message` patch (step 3) that must be read back and asserted; anything the patch cannot reach, such as the attachment set or `toRecipients`, is a fresh `create_draft_email` and the superseded draft lingers for Deep to delete manually. Get the facts and the attachment set right in step 2.
- Leaving a superseded draft unflagged once a replacement exists. Deep sees two plausible drafts in one folder and may send the wrong one. Every replacement must restate in the same reply the exact subject of the draft to SEND and the exact subject to DELETE, so the choice never depends on opening either.
- **Leaving a draft's own gap unresolved after the draft exists.** A fact only the user can supply (a body detail, a domain choice, an unconfirmed date) has to be settled in step 2 or tagged `[CONFIRM: field]` and named on the decision card in the same reply: a gap filled after the fact is a whole-body patch with a read-back (step 3), not a second draft, and a card that does not carry the fill-list leaves the tag unread.
- **Pasting the run's own verification header into the draft body.** The `[BOT: verify before sending: [CONFIRM] ...]` block is output for the reply and the decision card, never body content; it ships verbatim to the recipient if it lands in the mail. The body carries only inline `[CONFIRM: field]` tags, and the full confirm list lives in the reply.

## Verification

- [ ] Drafts and Sent searched for this ask before staging; any superseded draft named SEND or DELETE.
- [ ] Draft read back with `isDraft: true` and expected recipients and subject.
- [ ] Attachment present in the read-back, or the reported reason is a quoted tool error, not an unattempted "too fragile".
- [ ] Attachment read back with exact filename and size; content-hash match when the file's contents are in question.
- [ ] Reply contains the clickable `webLink`.
- [ ] After any re-attach, the attachment list shows exactly the intended files (old ids deleted), and for content questions the downloaded bytes match the local file.
- [ ] Nothing was sent without explicit approval; on an approved send, read-back shows `isDraft: false` (or the subject in Sent Items), never just the send call's success.
- [ ] Bulk pass: triage counts sum to the folder total, the stale threshold used was stated, and every non-ready draft names the signal that decided it.
- [ ] Every replacement draft on a live thread was created through the reply path and read back with its quoted history present in the body, not as a fresh mail with a `Re:` subject.
