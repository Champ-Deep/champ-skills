# Decommission readiness audit

## When to Use

Deep asks whether his projects are already on the target platform, whether an
old host (Railway and similar) can be cancelled, or wants a migrate/retire
readiness verdict before a cutover. Code-layer removal inside one deploy is
`risky-changes`; repo-level assessment is `champ-portfolio-triage`.

Read-only. Prove, per project, that a working counterpart exists on the target host and that the data has a verified backup, before anything is deleted. Source platform to target platform: Railway to Cloudflare and similar retire or migrate asks. Also covers the wiring a moved service needs on its new host: variables, shared secrets, and the counterpart route they point at. The deliverable is an evidence table plus a `needs_input` decision card with A/B/C options and a recommendation first. Never delete, deploy or change DNS during the audit.

## Always-on rules

- **Check the frontend host too, not only the backend.** When the ask says "is this already on X", fetch the app's own served HTML and grep it for the API base. A frontend host whose JS calls a relative `/api` is redundant: the backend on the target host already serves that same app, and deleting the frontend host loses nothing. Deleting the redundant host does not affect anything that does not ship in that HTML, which makes it the cheapest possible decommission and the one to propose first.
- **Never present a split arrangement as an option.** Do not offer "frontend on one host, API on another" when the API's host can serve the frontend too: one platform end to end is Deep's standing preference, so a second host is something to remove, not a fallback to preserve. Offering it invites a choice that has already been answered.
- **Answer "what does this deployment need" from the artifacts, never from memory.** Grep the source for the names it reads, list what the deployment already holds (`wrangler secret list` returns names only), and diff the two. For an integration, also diff the counterpart's open PR for environment additions, because the route that is not merged yet is where an undeclared variable comes from.
- **Wire an integration in dependency order: consuming route deployed, then shared secret set, then backlog backfilled.** A secret set before the other side's route exists turns every call into a failure that counts against the retry budget, so the records the integration exists to move get parked before it ever succeeds. Prove one real record end to end before sending the backlog, and un-park anything already parked instead of re-importing it.
- **A deletion is authorized, not silent.** "Never delete during the audit" means never without an explicit instruction naming the target: stage it as option A on the decision card, delete only on his word, then verify in the same pass (the old hostname answers 404/410, the surviving hostname still serves the app) and say in the reply that the deletion happened at his instruction.
- **Live response headers are the authority, not platform inventory.** A domain listed under a platform's custom-domains list may be served by someone else entirely, and a proxied record pointing at the old origin still answers. Probe every hostname.
- **Never delete before a verified backup.** Volumes and managed databases hold the only copy of data. Check `pg_dump`/`mongodump` availability up front; if the tool is missing, the backup step in the card names the install first. Say this in the report explicitly.
- **Read secret names, never values.** Cloudflare `/workers/scripts/{w}/settings` returns secret names only; plain-text vars are readable and are where an origin hostname hides.
- **Counts in the decision card come from the same computed table as the body.** Type them once, programmatically, and reconcile: a card whose summary count disagrees with its own lists gets corrected in a comment, because the summary is what downstream readers quote.
- **Team-owned repos need an owner ack before delete.** Attribute each project to the GitHub repo owner first; a project built from a teammate's account is their call, staged as a recommendation only.
- **End the report with a `Not checked:` section.** Name billing, data row-level parity, anything inferred from a proxy signal. An audit that only lists findings invites the reader to assume the rest was verified.
- **"All your data is there" is a parity check, not a copy log.** After a re-sync (usually `INSERT OR IGNORE` of new rows only, so nothing edited on the target is clobbered), compare per-table record id sets and per-owner row counts between source and target with a script kept in the repo, print the mismatched ids, and report the two totals and the per-owner column. A copy that "ran without error" proves the transfer started; only the id-set diff proves nothing was skipped, and the per-owner column is what Deep reads as his own cards being intact. Re-run the parity script after any later deletion on the target and say so, because the parity result is the gate the whole cutover rests on.
- **Deleting a host breaks whatever hardcodes its hostname.** Installed app wrappers (TWA, PWA, bookmarked shortcuts, deep links) keep pointing at the deleted address and fail only when someone opens them, which is after the audit. Search for the hostname in shipped clients before the delete and list them as a known break in the report.
- **The chat table is one row per project, with no lists inside a cell.** Deep reads the table first and decides from it; a paragraph or a comma-run covering several projects in one line makes him stop and ask for them separately, so split on his wording ("one for each") rather than keeping a tidy table. Extra detail, the full delete set and the long lists go in the card body, and a cell only holds the columns that support the verdict.
- **Traffic equal to zero over the whole window means the window is too short, not that the service is dead.** A metric series starts at its oldest returned sample, and anything idle since before that timestamp reads "never used". Widen the window and re-pull, because a longer look-back costs one query and the wrong verdict retires a live project.

## Procedure

1. **Inventory both sides in code, dump to scratch.** Source platform via its API (see `references/railway-graphql.md`): projects, services, service instances, custom domains, environments, volumes. Target host via its REST API (see `references/cloudflare-parity.md`): zones + DNS records (read `proxied` and the record target), workers scripts and their settings bindings, pages projects, account subdomain. Write JSON to `~/.hermes/cache/scratch/` and print compact rows; the raw files are cited in the report. Include the target host's cost-bearing resources in the same dump: containers with their size, instance count and owning script, and durable object namespaces with their script. When the ask names the bill or a cancellation, price that side as well: `references/cloudflare-cost-audit.md`.
2. **Measure liveness per service, not per project.** A window of outbound network bytes summed over daily samples tells you in use versus idle; treat CPU as a relative signal only, never quote the sum as a percentage. Start at 7 days when the question is "is this used now", widen to months when the question is "when was it last used" (a 7-day window returns zeros for a dormant project, which is silence, not a date). Loop with sleeps, save the rows, and sort the report on this number.
3. **Probe every hostname with live headers** (`curl -sS -o /dev/null -m 15 -D - https://HOST`, threaded, and record the SSL errors too):
   `cf-ray` alone = target host serves it; `x-<source-platform>` = old host still serves it; **both** = target host is proxying the old origin, so the migration is front-half only; `x-vercel` or another third host = it never belonged to either side; a certificate error on a `www` variant while the apex answers means the cert has no SAN for that name, report it as its own defect.
4. **Classify each project into exactly one bucket:** ready to retire (target host serves it, old host idle or failing), moved but old host still carrying load (data, DNS, IP dependency or auto-deploy), front-half only (target proxies the old origin), no counterpart on the target. Buckets must be exhaustive; every project lands in one.
5. **Check the data gate per project.** Volume sizes and DB types from step 1, plus repo docs for the documented cutover plan (search deploy/runbook files for the source platform's name). A documented resync that has not run yet is a blocker, not a done migration. When it has run, verify it with a parity script (per-table id sets, per-owner counts) rather than the importer's exit status, and keep the script in the repo so the check is rerunnable.
6. **Search the vault for prior rulings** on this migration before proposing anything: decision desk notes and open cards already hold cutover gates and named decisions. Cite them in the card so you do not re-ask a question with an answer.
7. **When the ask includes a cost or a cancellation, price the target host too** (`references/cloudflare-cost-audit.md`). Running instances of a container platform dominate the bill, so count them, find the ones no code uses, and put both totals (estimate, and the delete set) in the decision card.
8. **Open one `needs_input` card** with the bucket table in the body and three options, recommendation first. Then reply in chat with the same table: short verdict, one table, decision card, and the `Not checked` list.

## Pitfalls

- **Do not infer idle from the logs endpoint alone.** Request logs attach to a specific recent deployment and can return zero rows for a service that is busy; the 7-day egress metric is the liveness source, logs only add the hostnames that called in.
- **A health check hitting the old origin counts as traffic.** One request on a monitoring path is not a user; name the path when it is the only evidence, so the reader does not treat it as demand.
- **Staging and preview workers on the target host do not count as a counterpart.** A project with only preview/staging scripts while its production domain answers from the old host is unmigrated; match on production role, not on name similarity.
- **Grep the repo docs, not just the APIs, for hidden couplings.** Static IP allowlists, webhook receivers and auto-deploy hooks keep a retired project alive in practice even when all traffic has moved; these are the findings that change the recommendation.
- **Read each project's `createdAt` against the metric window start.** A project created inside the window reads "idle since <window start>" in a last-used table when the truth is "idle since creation", and a weeks-old project with a large DB and no repo is an unknown, not a retire candidate. Hold it until someone names it.
- **Upstream-fork stacks (Dograh, self-hosted Convex, n8n) cannot move data into a Cloudflare container.** Container disk is ephemeral and D1 cannot back upstream Postgres code without a fork-breaking rewrite. Put one data-home decision (managed Postgres vs D1 rewrite vs hold) on the card before writing their migration briefs, rather than deciding it per card.
- **A hostname moving onto a Worker through Cloudflare for SaaS needs its route as a runbook step:** the custom hostname, the fallback origin and a Worker route on the SaaS zone are three separate objects. When the customer's own zone is on Cloudflare and proxies the record (orange cloud, O2O), a route on the custom hostname (`share.example.com/*`) never fires: only the CNAME target route (`customers.saas.com/*`) or `*/*` does, and a grey-cloud record is the reverse (Cloudflare docs, Workers for Platforms, Hostname routing, O2O table). Add both specific routes, or `*/*`, and name the record IT must set (type, target, proxy status). A pre-flip `curl --resolve <custom host>` to a Cloudflare IP proves nothing while the customer zone still owns the name: it returns the old origin. Probe the CNAME target (`https://customers.saas.com/health`) instead. Read `GET /zones/<id>/workers/routes` before writing the cutover order; one ChampBeam runbook deferred the route to a dashboard card while the champbeam.com zone had 0 routes, so the DNS flip would have landed on no Worker. Every gate in the runbook gets a readback command and a pass condition.
- **A runbook step that creates a cloud object starts by reading whether it exists:** grep the board for the object's name and id (`sqlite3 ~/.hermes/kanban.db "select id from tasks where body like '%<hostname>%'"` plus the same on `task_comments`) before writing "Deep adds it" or "does not exist yet". One ChampBeam runbook told Deep to add the custom hostname share.lakeb2b.com while two cards recorded it as created on 10 Nov (id edf15e0b...) and `moved` on 20 Nov. A Cloudflare for SaaS hostname in `moved` is deleted after 7 days (Troubleshooting page; PATCH restarts validation), and a re-add rotates the ownership TXT already sent to IT. So the step is GET by hostname, PATCH if `moved`, compare the TXT with the one in the IT draft, and stop for Deep if the hostname is gone. The same grep finds sibling cards that own the same steps.
- **A header-absence watch must fail closed:** `curl ... | grep -c '^x-railway'` logs 0 when curl times out, so a dead host reads as 7 clean days. Log the status line and `cf-ray` too, and count a day only when the status is 200, `cf-ray` is present and the old platform's header is absent.
- **The old host stays up after a data cutover, and its own code still points at the host you just deleted.** Anyone who opens the legacy app then sees it broken and reports the migration as broken. Name it as an expected consequence ("the legacy app's screen is gone, its API and data are the archive"), and fix it in the same pass by retargeting the legacy frontend to the surviving hostname or stating that the legacy app is now API-only.
- **A volume snapshot is not a restorable backup when the data is encrypted with a key held in a service variable.** n8n's credentials in Postgres need `N8N_ENCRYPTION_KEY`, which lives only in Railway variables when the `.n8n` volume is empty. For each backed-up stack, list the variable NAMES that decrypt or sign its data and put them on the migration card, never the values. On Railway, a FAILED service with `stopped: true` has no readable volume: both `railway ssh` and `railway volume files list` refuse without an active deployment, so record it as not captured rather than redeploying.
- **Before offering a resource as a delete option, grep the board for its name and re-read its live state the same day.** A cleanup card's verdict column is a label from the day it was written: one called `deependhq-assistant-v2test` a test copy when it was the isolated rehearsal Worker an open release card depended on, and priced three orphan containers as running nonstop when they sat at 0 instances five days later. Run `select id,status,title from tasks where status not in ('done','archived') and body like '%<name>%'` and the live inventory before the option reaches Deep; if the check only happens after he approved, hold that item, say the label was wrong, and delete the rest.
- **GraphQL 400s from the source platform usually mean a bad field in the projection, not a dead API.** Catch the HTTP error, read its body, and retry with a reduced field set instead of concluding the data is unavailable (see `references/railway-graphql.md`).
